# 設計判断の記録

このドキュメントは wkr-macos で **何を採用し、何を採用しなかったか、その根拠** を記録します。
仕組みそのものの説明は [how-it-works.md](./how-it-works.md)、配列表と綴りは
[layout-reference.md](./layout-reference.md)、公開可能な検証結果は [verification.md](./verification.md) にあります。

## 1. 目的

JISキーボードの物理キー列を「わから配列」として解釈し、既存のApple日本語入力へ渡す。
中心となる要件は次のとおり。

- `E` を押した時点で「か」を扱える。
- 続けて `K` を押すと「き」になる。
- `E S K` は「か」→「かさ」→「かし」となる。
- `W K R` ではなく、`W E R` で「わから」となる。
- `かな` で有効、`英数` で無効になる。
- 最終的なかな列はApple日本語入力の未確定文字列としてSpace変換できる。

## 2. 非目的

- 独自のかな漢字変換エンジンを作ること。
- Apple日本語入力の私有APIや内部データへ依存すること。
- すべてのアプリ、リモートデスクトップ、ゲーム、仮想環境へ対応すること。
- App Store配布、自動更新、設定同期。
- 上流 `wkr-layout` の曖昧な記号規則を推測で確定すること。

## 3. 前提として確認したAPI

- `CGEventTap` は低レベル入力イベントを監視・フィルタできる。
- 現行SDKに `CGPreflightListenEventAccess`、`CGRequestListenEventAccess`、
  `CGPreflightPostEventAccess`、`CGRequestPostEventAccess` がある。
- JISキーコード `kVK_JIS_Eisu = 0x66`、`kVK_JIS_Kana = 0x68` が現行HIToolboxヘッダにある。
- TISには現在の入力ソース取得、入力ソース選択、選択変更通知がある。
- `IsSecureEventInputEnabled()` で、いずれかのプロセスがSecure Event Inputを有効にしているか確認できる。

一方、**外部プロセスからApple日本語入力の未確定文字列を直接編集する公開APIは確認できませんでした。**
これが、Unicode直接注入ではなく標準ローマ字の再送を主経路にしている理由です。

## 4. 変換モデル

### 4.1 正規化ルール

わから配列を、物理キー列からかな／記号出力へのTrieまたは有限状態トランスデューサとして表す。

各ノードは少なくとも次を持つ。

- `children`: 継続可能な物理キー。
- `output`: そのノード単独で成立する出力。
- `isAmbiguous`: 単独出力があり、かつ子ノードもあるか。
- `source`: 上流URL、revision、元規則。

入力処理は、未定義の次キーを捨てず、直前の成立出力を処理した後で同じキーをルートから再処理する。これにより `E S K` の `S` を失わない。

### 4.2 上流データの扱い

初期PoCではREADMEとテーブルの一致が明確なコアかな規則だけを正規化した。基本接続の成立後、同じrevisionからかな全行、小書き、特殊かな、JISで一意な記号行まで正規化範囲を拡大した。

2026-08-11の調査では、Google日本語入力用 `romantable.txt` とazooKey用TSVの記号領域に次の疑いが見つかった。

- `y`、`■x` の重複。
- `ば{` など区切りまたはキーの誤りらしい行。
- `{『`、`}』` の区切り欠落。
- 一部行への制御文字・置換文字混入。
- 記号の対応関係が2形式間で一致しない箇所。

したがって、生ファイルをそのまま実行時にロードしない。`WKRLayout.rules` をrevision固定の正規化スナップショットとし、かな14行、単打、前置小書き、`T`レイヤー、JISで一意な`Y`記号レイヤーを215規則として置く。JIS括弧キーは2026-08-12にApple日本語入力への素通しへ変更し、規則から外した（5.3参照）。重複、制御文字、区切り欠落、JISで物理キーを一意に決められないANSI記号行は `WKRLayout.quarantinedUpstreamEntries` に隔離し、実行時Trieへ入れない。

## 5. 出力方式

### 5.1 deferred-romaji（安全方式）

曖昧な接頭辞は、継続しない次キーまたは確定操作が来るまで保留する。

例:

1. `E` を押す: 内部状態は「か」だが、まだ出力しない。
2. `K` を押す: `EK → き` が確定したため、Apple日本語入力へ標準ローマ字 `ki` を再送する。
3. `E` の次に `S` を押す: `E → か` を `ka` として再送し、`S` を新しい曖昧状態として保持する。
4. Spaceが来る: 保留中の出力を先に再送してからSpaceを通過させる。

利点:

- 外部の未確定文字列をBackspaceで書き換えない。
- 内部状態と対象アプリの状態がずれにくい。

欠点:

- あ段の見た目が原則1キー遅れる。
- 行末ではSpace、Enter、句読点、タイムアウト等のflush設計が必要。

タイムアウトによる自動flushは誤分岐を生み得るため、最初は境界キーによるflushだけで評価し、必要性を実測してから追加する。

境界キーは一律に扱わない。

- Space、Return、句読点、Tab、カーソル移動を入力中に検出した場合は、保留出力を現在の対象へ順序どおり送ってから原イベントを通す。
- 保留入力だけがあり画面へまだ出ていない状態でBackspaceを受けた場合は、Backspaceを消費して保留入力を取り消す。原イベントを通して既存本文を削除してはいけない。
- 入力ソース通知やアプリ切替通知を、切替後に初めて受けた場合は、別の対象へ誤送信せず保留状態を破棄する。
- Command / Control / Option付き操作、Escape、Undo/Redoは、「flushして通す」「破棄して通す」「保留分だけ消費する」の期待挙動をケースごとにテストで固定する。

### 5.2 optimistic-romaji（即時方式）

曖昧ノードの単独出力を、Apple日本語入力が受理する標準ローマ字として即時再送する。継続キーが来たら直前の仮出力をBackspaceで削除し、新しい標準ローマ字列を再送する。

例:

1. `E` を抑止して `k` `a` を合成送信し、「か」を表示する。
2. `K` を抑止してBackspaceを送り、`k` `i` を合成送信し、「き」に置き換える。

この方式はBackspaceの単位とIMEの状態に依存する。TextEditだけで成功しても既定化せず、NotesとSafariでも同じ結果になることを最低条件とする。prefix-romajiは取り消しが必要な枝を66件に限定し、多くの枝で仮かなの差し替えを避けるため、現在この方式は実験用途に留めている。

実装では削除回数をグローバル定数にせず、直前の仮出力を識別する正規化規則IDごとの `OptimisticDeletionProfile` とした。全行の単一かな仮出力はBackspace 1回、`X → ふぁ` は2回を実験値として設定する。`E → か` の1回削除はTextEdit・Notes・Safariで成立済みだが、他行と `X` は実測前なので `--allow-unverified-optimistic` がない起動は引き続き拒否する。削除プロファイルがない規則の置換は、原キーや既存本文を推測で削除せずfail closedで抑止する。同じ出力を確定する `EH → か` 等ではBackspaceも再送も行わず、内部の仮状態だけを確定する。

### 5.3 prefix-romaji（ちらつき抑制方式・2026-08-12追加、常用方式）

通常のローマ字入力に近い見え方で、1キー目から表示を出す方式である。共有接頭辞がある曖昧ノードでは、そのノードから到達し得る全ローマ字出力が共有する接頭辞の先頭1文字を送り、確定時に残りを送る。共有接頭辞がない一部ノードは自ノード出力または仮表示を先に流し、既知の継続枝ではBackspace 1回で取り消す。したがって取り消しをゼロにする方式ではなく、発生する枝を66件に固定している。

例:

1. `E` を押す: `か` 行の全出力 `ka` / `ki` / `ku` / `ke` / `ko` / `kya` / `kyu` / `kyo` が共有する `k` だけを送る。画面表示は `k`。
2. `K` を押す: `EK → き` が確定するので残りの `i` を送る。画面表示は `き`。
3. `E` の次に `R` を押す: 先に `E` の残り `a` を送って `か` を確定し、続けて `ら` 行の共有接頭辞 `r` を送る。画面表示は `かr`。
4. Enterが来る: 保留中の残り母音 `a` を先に送ってからEnterを通す。押鍵数は変わらず `わから` が確定する。

方針は「1キー目で必ず表示を出す」である。Trieの各ノードに、部分木の全ローマ字出力が共有する最長接頭辞と、実際に流す文字列を事前計算する。流す量は次の順で決める。

1. 共有接頭辞が空でなければ、その1文字目を流す。全枝を保護できるので取り消しが起きない。
2. 共有接頭辞が空でも、同じ1文字目で始まる出力が他にもあれば1文字目を流す。`X` 行の `ふぁ` / `ふぃ` / `ふゅ` / `ふぇ` / `ふぉ` は `f` を共有するため、`X` は `f` を流す。
3. その1文字目で始まる出力が自分だけなら、**自ノードの出力を全部流す**。1文字だけでは何も保護できず、かなも表示されないためである。`H → あ` と同じ即時表示を `U → や`、`I → ゆ`、`O → よ` でも得るのがこの規則である。後置小書きを廃止した2026-08-16以降、これらのノードは枝を持たない終端になり、取り消しも起きない。

`Y` の仮表示は、その部分木が共有する接頭辞である `z` になる。矢印4件が `zh` / `zj` / `zk` / `zl` というローマ字出力を持つためで、他の根と同じ規則から導出される。以前はローマ字出力が1つも無く `WKRLayout.symbolLayerProvisionalRomaji` で `y` を明示していたが、その明示は不要になった。記号55件は仮表示の `z` をBackspace 1回で取り消してから注入し、矢印4件は `z` をそのまま継ぐので取り消しが起きない。確定文字である `■` 等を仮表示に使わない方針は変えない。記号が決まる前に本文を書き換えることになるためである。

後置小書きは上流 v1.1 で全廃した。母音キーの後の `T` を必ず吸い、`K` `T` `;` が `いぇ` ではなく `ぃえ` になるように、基本かな＋前置小書きの組み合わせを潰していたためである。副次的に、仮表示がすでにかなへ合成されている唯一の枝が無くなり、取り消しはすべて未合成のローマ字1文字の削除になった。

取り消し数は**表示されている単位**で数える。`k` や `f` のような未合成のローマ字は1文字が1単位、`や` のように送出2文字がすでに1かなへ合成されている場合は1単位である。ノードごとに「流した文字列が自ノード出力そのものならかな数、そうでなければ文字数」を事前計算して保持する。optimisticのように規則IDごとの削除回数を人手で与えるのではなく、表から導出する。

分岐は2種類ある。

- 共有接頭辞に基づく分岐: 到達し得る全出力が同じ1文字目で始まるため、取り消しは発生しない。か行、さ行、た行、な行、は行、ま行、ら行、が行、ざ行、だ行、ば行、ぱ行、わ行、`T` 前置小書きが該当する。
- 自ノード出力に基づく分岐: 一部の枝が別の1文字目を持つため、その枝へ入るときだけ、自分が送った1文字をBackspace 1回で消してから正しい出力を送る。

取り消しが起きる規則は次の66件で、テストで集合として固定している。想定外の規則が取り消しを始めたらテストが落ちる。

- `X` 行の4件（`XY → てゅ`、`XU → てぃ`、`XI → でゅ`、`XO → でぃ`）: 行内で `ふ` / `て` / `で` が混在するため、`ふぁ` 系の `f` だけを流す。
- 行の1文字目を継がない出力6件（`WJ → ヴ` と `T,` / `T.` / `T/` はUnicode、`EY → ヶ` は `lke`、`WY → ゎ` は `lwa`）。`WU → ゐ` の `wyi` と `WI → ゑ` の `wye` は `w` を継ぐので取り消しが起きない。
- `Y` 記号レイヤー55件: 仮表示の `z` をBackspace 1回で取り消してからUnicodeを送る。矢印4件は `z` を継ぐので該当しない。

ローマ字出力規則については、送出ローマ字からBackspace分を差し引いた最終文字列が宣言ローマ字と一致することをテストしている。Unicode出力規則については、仮表示をちょうど取り消し、最後のactionが宣言Unicodeになることを別テストで固定している。

境界とキャンセルの扱いは次のとおりである。

- Space、Return、Shift+Return、Tab、句読点は、保留中の残りを先に送ってから原キーを通す。Shift+Returnは多くのアプリで改行なので、Returnと同じ確定扱いにする。Shift付き句読点（JISの `？` = Shift+/ など）も、未対応Shift組合せとして保留を捨てず、句読点と同じ確定扱いにする。
- Shift+英字のように配列へ割り当てのないShift組合せは、保留を捨てずに確定扱いにする。Apple日本語入力ではShift+英字が「英字」モードへの切替なので、`G` の後の `Shift+O` は `は` を確定してから `O` を通し、`はO` になる。以前は「未対応の修飾キー付き入力」として保留を捨てており、送出済みの `h` が取り残されて `hO` になっていた。
- 出力を持たないノード（`T` や `Y` の単独状態）でSpace等の境界キーを受けた場合、仮表示の文字は削除しない。画面に出したものをWKRが自発的に消さない方針をEscapeと揃える。明示的なBackspaceだけが取り消し操作である。
- Control付きのショートカットは変換先で分ける。かな変換は保留中のかなを先に確定してから原キーを通す。`W` `E` `R` の後のCtrl+Kは `ワカr` ではなく `ワカラ` でなければならない。transducerの保留がすでに終わっていてもApple日本語入力側にはmarked textが残り得るため、かな変換は常に境界経路を通し、Unicode注入ゲートを安易に空へ戻さない。
- ローマ字変換は保留を完成させず、Apple日本語入力へ流した仮ローマ字までを変換させる。末尾の `a` を補うと、物理入力にない文字まで全角／半角ローマ字へ変わるためである。prefixモードは表示済みの子音をそのまま使い、deferredモードはまだ画面に出していない同じ仮ローマ字だけを送り、optimisticモードは仮かなを削除してその仮ローマ字へ戻す。ローマ字変換後も未確定文字列が残るものとして保守的に扱い、Unicode注入ゲートの文字数は0へ戻さず、英字打ち直し用journalだけを破棄する。
- 現在ローマ字変換側へ分類するのは、今回の利用設定として報告された修飾なしのControl+L / Control+;だけである。Shift併用は従来のかな完成側を保つ。Appleの既定・Windows風など複数設定の割当てを和集合にすると、選択されていない設定では別操作を誤分類する。選択中のキー設定を公開APIで判別できないため、それ以外のControlは従来どおりかな完成側へ倒す。F9 / F10もControl経路ではないため未対応である。Controlショートカットのautorepeatは、初回で保留を処理した後、そのまま通してUnicode注入ゲートの保守的な文字数を維持する。CommandとOptionは従来どおり破棄して素通しする。これらのショートカットはフォーカスを移し得るため、合成ローマ字が別の場所へ届く危険があるためである。
- Escapeを含むreset系イベントでは、WKRは内部状態だけを破棄し、合成イベントを一切送らない。未確定文字列はApple日本語入力の所有物であり、Escapeでどうなるかは IME 側の仕様と前面アプリに従う。2026-08-14の実機確認では、TextEditはEscape 1回ごとに「直前の文節をひらがなへ」「未確定全体をひらがなへ」「未確定を破棄」と段階的に戻り、Claude.appでは削除されずそのまま確定した（範囲は [verification.md](./verification.md) にある）。この結果を受けても方針は変えない。取り消しが段階的で、しかもアプリによって結果が変わる以上、WKRが独自の削除を足すと素のローマ字入力との食い違いがむしろ大きくなるためである。Escapeの判定は修飾キーフィルタより前に置き、resetの理由がEscapeとして記録されるようにする。
- 保留状態を捨てるresetはnotice levelでログする。捨てられた保留は、送出済みローマ字が未確定表示に取り残される唯一の経路であり、原因の切り分けにはその理由が要るためである。
- Backspaceは送出済みローマ字ちょうどを消し、既存本文へ触れない。

この方式のために、行内で1文字目が割れていた綴りをApple日本語入力が受理する訓令式へ変更した（`ち`=`ti`、`ふ`=`hu`、`じ`=`zi` など）。小書きは実測に基づき `x` 系から `l` 系へ統一した。**かな自体は変更していない。** 変更の全一覧と実測の根拠は [layout-reference.md](./layout-reference.md) にある。

#### JIS括弧キーを横取りしない理由

`「` / `」` / `『` / `』` はUnicode直接注入で送ると即座に確定し、Spaceで `（` 等へ変換できなくなる。JIS括弧キーはApple日本語入力自身が同じ文字を未確定文字列として出せるため、規則から外して素通しし、`（` / `＜` と同じ変換体験に揃える。対象は `WKRLayout.passThroughKeys` に4件として明示し、どのモードでも素通しすること、保留中のかなは先に確定することをテストで固定している。

### 5.4 Unicode直接注入（特殊かな・記号のみ）

通常かなはApple日本語入力の未確定文字列とSpace変換を維持するため標準ローマ字で送る。ローマ字で表現できない出力だけを `CGEvent.keyboardSetUnicodeString` のマーカー付きイベントで送る。Unicodeイベントを無視するアプリがあり得るため、この経路はアプリ別の物理確認を必要とし、通常かなへは広げない。

対象は58件である。`Y` 記号レイヤー55件と `T,` / `T.` / `T/` の全角約物3件。

2026-08-16に、Apple日本語入力自身のローマ字表 `RomajiRule_Default.txt` を確認した。447行のうち、かな以外を出力する規則は矢印4件（`zh` / `zj` / `zk` / `zl`）だけである。**残る記号にローマ字の綴りは存在しない。** 読みを打ってSpaceで変換すれば出せるものはあるが、候補の順位が学習や辞書で変わるためWKRからは決め打ちできず、2. 非目的の「推測で確定しない」に反する。

実測できた綴りは規則へ取り込み、8件をこの経路から外した。

| 規則 | 綴り | 備考 |
| --- | --- | --- |
| `EY → ヶ` | `lke` | 小書きは `x` 系ではなく `l` 系（5.3参照） |
| `WU → ゐ` | `wyi` | `w` を継ぐので取り消しなし |
| `WI → ゑ` | `wye` | 同上 |
| `WY → ゎ` | `lwa` | |
| `YH` `YJ` `YK` `YL → ←↓↑→` | `zh` `zj` `zk` `zl` | ローマ字表にある4件 |

`WJ` は綴りだけでなく**かなを変えた**。`vu` が返すのは `ゔ`（U+3094）で、配列が指定していた `ヴ`（U+30F4）とは別の文字である。ひらがなモードでカタカナの `ヴ` を出す綴りはことえりのローマ字表に無く、`v` で始まる12件はすべて `ゔ` 系を返す。`ヴ` を注入し続けると、その場で確定して未確定文字列から出てしまうため `ゔぁ` `ゔぃ` `ゔぇ` `ゔぉ` `ゔゃ` `ゔゅ` `ゔょ` を作る手段が無くなる。`ゔ` にすれば7件が既存の小書き規則との組み合わせで作れ、Space で `ヴ` へ変換できる。これは綴りではなく**かな自体の変更**であり、`QY → ヵ` の追加および後置小書きの廃止とあわせて上流 `wkr-layout` ver 1.1 へ反映済みである。根拠は [layout-coverage.md](./layout-coverage.md) にある。

#### 未確定文字列があると届かない（2026-08-16 実測）

2026-08-16の実測で、この経路には**未確定文字列がないときにしか届かない**という制約が
あることが分かった。実測は [verification.md](./verification.md) にある。要点は3つである。

- 未確定文字列があるとイベントは黙って捨てられ、1打鍵が失われる。67件全体に及ぶ。
- 直前のBackspaceとの競合ではない。Backspaceを出さないdeferredでも同じである。
- 仮想キーコードを `kVK_ANSI_A` 以外にすると、未確定の有無に関わらず届かなくなる。
  **この経路はApple日本語入力がそのイベントを処理してくれることに依存しており、
  アプリへ直接届ける道はない。** CGEvent層での回避策は無い。

注入前に未確定文字列を確定させる手段も限られる。`かな` は未確定があると何も起こさず、
未確定がないと再変換を走らせるため、確定手段として不適格であるうえ合成で送ってはいけない。
残るのはReturnだけで、ライブ変換が有効ならその推測を確定させることになる。**採らない。**
記号1つのためにSpace変換の機会を奪い、判定が外れればチャットアプリで誤送信になる。

#### 採る方法: 未確定があるときは注入しない

届かないと分かっている状態では何も送らず、notice levelでログへ残す。**現状で一番悪いのは
「黙って1打鍵が消える」ことで、利用者が原因を知る手段がない。** 何もしないと決めれば、
少なくともログから分かる。

判定は「Apple日本語入力の未確定文字列に、WKRが完成させたかなが残っているか」である。
WKRは自分が送出したローマ字を数えているので、そこから今回の結果が消す仮表示分を引けば、
残りが0かどうかで判定できる。仮表示（`Y` の `y` など）はUnicode出力と同じバッチの
Backspaceで消えるため、それ自体は未確定文字列を作らない。

数え方はfail closed側へ倒す。

- `.romaji` を送ったら文字数を足す。`.backspace` は引く。
- Return、Escape、マウス、アプリ切替、カーソル移動、入力ソース変更では0へ戻す。
- **Space、Tab、句読点では0へ戻さない。** Spaceは変換であって確定ではなく、句読点が
  確定を伴うかは未確認である。確定したと誤って判断すると、届かない注入をまた送ることになる。
- 判定が保守的すぎて記号が入らない場合、利用者は確定してから打ち直せる。逆向きの誤りは
  1打鍵の消失として現れ、気づけない。

この判定は、8. 英字への打ち直しの前提でもある。「注入した＝届いた」が保証されないうちは、
注入した確定済み文字数を数えて打ち直すことができない。

#### `Y` 記号レイヤーを無効にする選択肢

未確定文字列がない状態でも、記号はその場で確定する。**変換の余地なく確定することが
望ましくない場面が多い**という判断から、`Y` 記号レイヤー55件を丸ごと外す選択肢を
`--symbol-layer off` として持つ。既定は `on` で、従来の挙動を変えない。

**矢印4件は外さない。** ローマ字で送るようになったので即確定せず、文中でも動き、
Space変換も読み戻しも効く。無効にする理由が矢印には当てはまらない。結果として `Y` は
矢印の前置キーとして生き続け、仮表示 `z` を出す。

この選択肢は `Y` から始まるUnicode出力55件だけを外す。`WJ → ヴ` と `T,` / `T.` / `T/` は
同じ制約を持つが、記号レイヤーではないので対象にしない。

**`--symbol-layer off` の意味づけはまだ確定していない。** `Y` キー自体を空けたい場合は
矢印も外して `Y` を抑止する形になるが、その判断は `on` の挙動を実機で確定させてから行う。

### 5.5 InputMethodKit（ラッパー不成立時）

InputMethodKitなら `setMarkedText` 相当の経路で自前の未確定文字列を管理できる。ただし同時にApple日本語入力を動かし、その変換エンジンだけを公開APIで利用できるとは確認できていない。採用する場合は「独自IME＋別の変換エンジン」という別プロジェクト級の判断になる。

### SafetyGate

- `IsSecureEventInputEnabled()` が真なら停止・リセットする。このAPIは現行SDKヘッダ上thread-safeではないため、event tap callbackで直接評価せず、main run loopのcommon mode Timerで確認する。

## 8. 英字への打ち直し（2026-08-14提案・実装済み、実機未確認）

### 8.1 解きたい問題

日本語入力モードのまま英単語を打ってしまったとき、Apple日本語入力の `英数` キー連打による
読み戻しは、物理キー列ではなくWKRが送った合成ローマ字を返す。`thing` のつもりで打った
`T` `H` `I` `N` `G` は `layunnh` になる。Apple日本語入力が保持しているのは受け取ったローマ字の
生列であり、物理キー列を知っているのはWKRだけなので、Apple日本語入力側に復元の材料はない。
実測は [verification.md](./verification.md) の2026-08-14エントリにある。

### 8.2 採らない方法

- **未確定文字列をWKRが取り消してから打ち直す。** Escapeも `英数` 連打も、必要な押下回数が
  アプリまたは未確定文字列の状態によって変わる。2026-08-14の実測では、TextEditはEscape 3回で
  未確定を破棄したのに対しClaude.appは1回で確定し、`英数` はTextEditで3回、Claude.appで2回だった。
  WKRが回数を決め打ちすると超過分が前面アプリへ漏れる。**未確定文字列を確実に取り消す手段は
  現時点で無い。**
- **`英数` の連打をWKRが検知して自動で置き換える。** ダブルプレスの閾値が非公開である上に、
  段数が上記のとおり非決定的なので、検知の起点を固定できない。
- **送るローマ字を物理キー列に寄せる。** かなとローマ字の対応は固定で、`ぁ` は `la` でしか出せない
  （`x` 系は連続入力で崩れるため2026-08-12に不採用）。物理キー列と一致させる自由度がない。

### 8.3 採る方法

段数の判断を利用者に任せ、WKRは決定的な部分だけを担う。

1. 利用者が `英数` を連打し、**画面にアルファベットが出た状態を目で確認する**（2回でも3回でもよい）。
2. そこで専用キーを1打する。WKRは送出済みローマ字の文字数ぶんBackspaceを送り、
   物理キー列から作った英字列を入れる。

この分担であればWKRは押下回数もタイミングも推測しない。アルファベットが出ている状態の文字列は
WKRが送ったローマ字そのものなので、**長さが分かる限りにおいて**置換は決定的である。英字列は現在の
ASCII-capableキーボードレイアウトから作り、JIS配列の記号キーでも打った通りの文字を得る。

ただし2026-08-14の追加実測で、**読み戻しでアルファベットへ戻るのは未確定の部分だけ**であることが
分かった。既に確定した部分はかな漢字のまま残る。したがって画面に現れるアルファベットの長さは
「送出済みローマ字の総文字数」ではなく「最後の確定以降に送ったローマ字の文字数」である。
文字数を多く見積もればBackspaceが確定済みの本文を食う。

この差が実害になるかどうかは、**確定の境界がWKRの観測できるキーで作られるかどうか**で決まる。
2026-08-14の追加実測では、Space・Enter・句読点を一度も押さずに
「きょうはいいてんきですね」程度の長さを打っても未確定文字列は分割されず、部分確定は起きなかった。
この長さの範囲では、境界はWKRが観測できるキーでしか生まれない。いずれも既存のreset条件に
入っているので、そこで文字数を0へ戻せば整合する。**これ以上の長さは未確認であり、
上限（8.4）で未確認の領域へ入らないようにする。**

### 8.4 保持する状態

- 未確定スコープの物理キー履歴（キーコードとShift状態）。
- 送出済みローマ字の文字数。

現在のトランスデューサは1かな分の保留しか持たず、`英数` キーの押下では
`invalidateContext(.inputSourceChanged)` で状態を捨てる。この機能は `英数` を押した**後**に
発動するため、**変換ゲートを閉じることと履歴を捨てることを分離する**必要がある。ゲートは今までどおり
即座に閉じてかなを作らず、履歴だけをTTL付きで残す。

履歴の上限は、プライバシーの担保（8.5）だけでなく**正しさの担保としても働く**。部分確定が
起きないことを実測できているのは「きょうはいいてんきですね」程度の長さまでなので、上限を
その範囲へ置き、超えたら履歴を捨てて何もしない。これで未確認の長さでは発動しない。
上限を緩める場合は、緩めた長さで部分確定が起きないことを先に実測する。

### 8.5 打鍵履歴の保持条件

AGENTS.mdの該当規定が禁じているのは「ファイル、標準出力、解析サービスへの記録・送信」であり、
プロセス内での保持は元から対象外である。とはいえ暗黙の解釈に頼らず、次の条件を明文化する。
AGENTS.mdの安全・プライバシー節にも同じ趣旨を1行置いた。

- 保持先はプロセスのメモリだけとする。ファイル、標準出力、ログ、ネットワークへ出さない。
  ログに出るのは権限状態、モード、入力ソースID、状態コード、エラー種別、集計件数までという
  既存方針は変えない。
- 打鍵数の上限を持ち、超えたら履歴を捨てて何もしない。古いものだけを落とすと、残った打鍵と
  送出済みローマ字の文字数が対応しなくなるためである。
- 寿命を持ち、経過したら捨てる。
- Secure Event Input、権限喪失、event tap無効化では即座に破棄する。
- それ以外の破棄条件は既存のreset条件に揃える。Enter／Spaceによる確定、句読点、マウスクリック、
  カーソル移動、アプリ切替、入力ソース変更（`英数` を除く）、Escape、修飾キー付き入力。

### 8.6 fail closedの条件

次のいずれかでは何も送らず、トリガキーだけを消費する。既存本文を推測で削除しない方針を優先する。

- 履歴が空、寿命超過、上限超過のいずれか。
- Backspaceキーが押された。取り消した量が既存本文に及ぶかどうかをWKRは判断できない。
- Unicode出力を通った。その場で確定するため読み戻しの対象にならない。矢印4件はローマ字に
  なったので対象に入り、`Y` `J` は `yj` へ戻せる。
- 取り消しの起きる枝を通り、**かつ削除した文字数を確定できない**。prefix-romajiの66件は
  文字数が分かるので対象に入る（8.6.1）。optimistic-romajiの規則ID別削除プロファイルは
  表示単位しか持たないため、従来どおり発動しない。
- Spaceによる変換を挟んだ。読み戻しが何を返すか未確認のため、文字数を信用できない。
- 最後の確定以降に送ったローマ字の文字数を確定できない。多く見積もるとBackspaceが本文を食うため、
  疑わしい場合は何もしない。
- Secure Event Input、権限不足、対象外の入力ソース、除外アプリ。

#### 8.6.1 取り消しの起きる枝を数える

当初は取り消しが挟まった時点で発動しないことにしていた。Backspaceの回数が表示単位で、
送出済みローマ字の文字数と対応しないためである。ただし対応しないのは**回数**であって、
トランスデューサ自身は消した文字数を知っている。`deleteEmittedRomaji` が消すのは
`emittedRomaji` ちょうどで、その文字数を `TransitionResult.deletedRomajiCharacters` として
返せば、履歴の文字数はそのまま引き算できる。

例。`E` `Y` は行の `k` を取り消して `lke` を送るので、画面に残るのは `klke` ではなく `lke` の
3文字である。履歴も 1 − 1 + 3 = 3 とする。`U` `T` は `や`（表示1単位、ローマ字2文字）を
取り消して `lya` を送るので、Backspaceは1回でも引くのは2文字、2 − 2 + 3 = 3 となる。
**この2つの数が違うことが、当初これを諦めた理由だった。**

2026-08-16に `E` `Y` `W` `Y` で読み戻しが `lkelwa`（6文字）を返すことを実測し、この数え方が
実際の表示と一致することを確認した。文字数を返せない経路（optimistic-romajiの削除プロファイル）
では `deletedRomajiCharacters` が0のままになり、従来どおり発動しない。

### 8.7 未解決の項目と注意事項

- **連打方式の実機確認が未了である。** コード方式（`英数`+Enter）は2026-08-15にTextEditで
  置き換えの成立を確認したが、既定を連打方式へ変えたあとの確認はしていない。
- **連打の間隔がApple日本語入力の2回押し判定とずれる場合の挙動が未確認である。** wkrの0.25秒より
  短いがApple日本語入力が2回押しとみなさない速さで叩くと、アルファベットが出ていない状態で
  発火し、本文を削り得る。**破棄してよい文書で先に試す。**
- **注意事項: 長い未確定文字列での部分確定は未確認である。** 2026-08-14の実測で
  「きょうはいいてんきですね」程度までは部分確定が起きないことを確認したが、それを超える長さは
  確認していない。上限（8.4）でその領域に入らないようにしているので実装は進められるが、
  上限を緩めるときは先に実測する。
- 逆方向（英数モードで打った英字を、わから配列として解釈し直す）は同じ履歴で実装できるが、
  今回の非目的とする。

### 8.8 トリガの決め方

既定は `英数` の**連打が終わったこと**である。0.25秒より短い間隔の押下を1つの連打とみなし、
最後の押下から0.25秒後に、2回以上あれば発火する。1回だけの `英数` は通常のモード切替なので
何もしない。

固定回数にしないのは、読み戻しに必要な押下回数がアプリによって違うためである。2026-08-14の実測では
Claude.appが2回、TextEditが3回だった。「素早い2回目で発火」にすると、Claude.appでは正しいが
TextEditではまだアルファベットが出ていない時点で発火し、本文を削る。連打の終わりを待てば、
利用者はそのアプリに必要なだけ叩けばよく、wkrは回数を知らなくてよい。

**2026-08-15に、`英数` を押しながらEnterというコードを先に実装して実機で確認したが、
操作として成立しなかった。** 置き換え自体は動作した（`english-fallback state=replaced keys=5`）
ものの、Enterを押す時点で `英数` が既に離れていることが多く、発火しない。押しっぱなしを
要求する時点で無理があった。コードの実装は残してあるが、既定ではない。

`英数` を押しながらのキーは、置き換えが起きなかった場合も前面アプリへ渡さない。この組合せは
明確に意図的な操作であり、素通ししてチャットアプリでメッセージを送ってしまうより、
Enterを1回失うほうが軽いためである。

連打方式は発火が event tap callback の外（main run loopのタイマー）になるので、合成イベントは
proxyを使わず `CGEvent.post(tap:)` で送る。自分のtapにも届くが、既存のマーカーで素通しされる。

トリガは `EnglishFallbackTrigger`（`eisu+eisu` / `eisu+return` / `eisu+tab` / `off`）で、
`--english-fallback` またはユーザーデフォルト `EnglishFallbackTrigger` で選ぶ。フラグが優先される。
設定ウィンドウはまだないが、値の置き場所を先に決めておけば、メニューバーを作るときに束ねるだけで済む。

### 8.9 英字列の作り方

`PhysicalKey.jisCharacter` がJISキーボードの刻印文字を返す。現在のキーボードレイアウトへ
問い合わせず固定表にしたのは、wkr-macosがJIS専用であり答えが1つに決まるためと、
event tap callbackの中に失敗経路を増やさないためである。JISの上段はANSIと1つずれている
（`Shift+2` は `@` ではなく `"`）ので、そこだけ明示している。

### 8.10 権限の再許可を起動側で吸収する

再ビルドしたbundleはad-hoc署名が変わるため、入力監視とアクセシビリティの許可が新しいidentityには
付いていない。アプリは権限を要求した直後に終了する。`CGRequestListenEventAccess()` が許可を
待たずに戻るからで、これは「権限が揃わなければ変換しない」という安全規則そのものである。

**この規則は変えない。** 代わりに `Scripts/start-app.sh` が、アプリが起動したままになるまで
再試行する。1回ごとに新しいプロセスなので、実行中のプロセスが権限の変化を観測できるかどうかに
依存しない。アプリ側で待って再確認する作りにすると、fail closedの条件が1つ増え、
「権限が無いまま生きているプロセス」という状態を持つことになる。起動側なら、待つのは
アプリではなくコマンドで済む。

2026-08-15に、同じ箇所（許可した後に起動し直さなかった）で2回止まったことがこの変更の理由である。

### 8.11 実装の状況

`WKRCore` の `EnglishFallbackJournal` に履歴、上限、寿命、破棄条件、fail closedの判定があり、
`EventTapController` が記録と発動を担う。`英数` のkeyDown／keyUpで押下状態を持ち、
resetの理由が `inputSourceChanged` のときだけ履歴を残す。

2026-08-15にTextEditとClaude.appで実機確認した。コード方式・連打方式とも置き換えは成立し、
コード方式は操作として成立しなかった（8.8）。先行するテキストを置いた状態でも削られたのは
送出済みローマ字だけで、本文へは届かなかった。確認範囲と未確認事項は
[verification.md](./verification.md) にある。

## 9. 打鍵頻度の記録とヒートマップ（2026-08-27追加）

### 9.1 解きたい問題

わから配列は上流の設計意図があって並んでいるが、**実際に自分がどのキーをどれだけ叩いているか**は
配列表からは分からない。指ごとの負荷が偏っていないか、親指に載せた `LT1(Space)` や `LT2(英数)` が
想定どおり使われているか、記号レイヤーを無効にしたら `Y` の打鍵がどこへ流れたか。
これらは実測しないと答えが出ない。

### 9.2 AGENTS.mdとの関係

AGENTS.mdの安全・プライバシー節は「キー列、入力本文…をファイル、標準出力、解析サービスへ
記録・送信しない」と定めている。**キーごとの累計回数はこの禁止の対象外だと暗黙に解釈せず、
明示的な例外として同節に1行を置いた。** 根拠は次の2点である。

- 禁じているのは「キー列」、すなわち順序を持つ打鍵の並びである。順序を落とした度数分布からは
  入力文字列を復元できない。`WKR` と `RKW` は同じ集計になる。
- 同節は「通常ログは…集計件数までとする」として、集計値そのものは許容している。

とはいえ度数分布も無害ではない。単独では文字列を復元できなくても、短い入力しか含まない期間の
集計は候補を絞り込む。だから**既定は無効**にし、数える範囲を次のとおり狭く取る。

### 9.3 保存してよいもの・いけないもの

保存するのは `(macOSの仮想キーコード, Shiftの有無) → 回数` と**暦日**だけである。

保存しないものを明示する。

- **打鍵の順序。** バケットは順序を持たない辞書であり、書き出しはキーコード順に並べ替える。
- **暦日より細かい時刻。** 「何時に何を打ったか」は残らない。日別バケットにしたのは
  「配列を変えた前後で比べたい」という用途に必要な最小の粒度がそこだからで、それ以上は取らない。
- **入力文字列、変換候補、クリップボード。** 既存方針のまま、一切扱わない。
- **アプリケーション名。** 前面アプリごとの内訳は取らない。取れば「どのアプリで何を打ったか」の
  プロファイルになる。

### 9.4 数えない条件

次のいずれかでは1回も数えない。**変換を行わない条件（`docs/how-it-works.md` 8節）とほぼ同じ
ゲートを使い、判定を二重に持たない。**

- 変換ゲートが閉じている。すなわち権限欠如、Secure Event Input、除外アプリ、
  対象外の入力ソースのいずれか。**Web のパスワード欄のように Secure Event Input を立てない
  入力先があるため、「Apple日本語入力ひらがなが有効な間だけ」という条件が実質的な防波堤になる。**
  パスワードをひらがな入力で打つ操作は成立しないので、この一致が偶然ではなく効いている。
- Command / Control / Option / Caps Lock を含むイベント。アプリ別ショートカットの利用傾向が
  ファイルに残るのを避ける。またこれらは既存方針でfail closedして素通しする対象でもあり、
  「変換していないキーは数えない」で一貫する。
- オートリピート。押しっぱなしは1打鍵とする。

**`fn`（`kCGEventFlagMaskSecondaryFn`）はこの一覧に入らない。** 名前に反して修飾キーの押下記録
ではなく、macOSがファンクションキー群のイベント全体に立てる識別子だからで、除外すると矢印キーが
原理的に数えられなくなる。経緯は9.7.1にある。

例外は `かな` / `英数` の2つで、これらは**入力ソースの一致だけを外したゲート**で数える。
この2キーは入力ソースを切り替えるキーそのものなので、ソース一致を条件にすると `かな` が
構造的に数えられなくなり、この配列がもっとも多用するキーの1つが図から抜け落ちる。
モード切替は打った内容を何も含まないので、Secure Event Input を含む他の条件はそのまま課したうえで
この1点だけ緩める。

### 9.5 event tapへの影響

修飾キーは keyDown ではなく flagsChanged で届くため、Shift や Corne の親指 Command は
既定のイベントマスクでは見えない。そこで **`--key-frequency on` のときだけ `.flagsChanged` を
マスクへ加える。** 無効時のイベントマスク・コールバック経路・1打鍵あたりの処理は、
この機能が無かったときと完全に同一である。flagsChanged 経路は観測専用で、常に元イベントを
そのまま返し、保留中のかなにも触れない（Shiftを押した時点で直前のキーの送出済みローマ字を
捨ててはならないため）。専用の修飾キーだけでなく、`LSFT_T(...)` の hold をファームウェアが
修飾キーに解決した場合も、この経路では同じ論理 Shift の押下エッジとして観測される。

コールバック内でやるのは辞書の1加算だけである。ファイルI/Oは main run loop の
Timer（120秒間隔）と終了時にのみ行う。AGENTS.mdの「event tap callback内で重い処理、
ファイルI/O、ネットワークI/Oをしない」をそのまま守る。

### 9.6 保存先と寿命

`~/Library/Application Support/io.github.yuhkis.wkr-macos/key-frequency.json` に、
ディレクトリ 0700・ファイル 0600 で置く。同じMacの他ユーザーが読むものではない。

**保持期間の上限は既定で設けない。** 当初は180日で切り捨てていたが、これは判断を誤っていた。

- この機能はオプトインであり、有効にした人は既に「集めたい」と決めている。
- ファイルが持つのは内容を含まない集計値で、プライバシーの担保は「順序なし・暦日より細かい
  時刻なし・0600・非送信」の側にある。保持期間はそこでは主役ではない。
- 実測で1日あたり3KB弱。10年で数十MB程度で、容量は制約にならない。
- **この集計がもっともよく答えられる問い——配列を変えて負荷が動いたか——は、いちばん古い
  データを必要とする。** 半年で消すのは、その問いを自分で潰すことになる。

上限が要る場合は `--key-frequency-retention <日数>` または `KeyFrequencyRetentionDays`
ユーザーデフォルトで指定する。指定すると書き出しのたびに窓の外を捨てる。`0` や負数は
「何も残さない」ではなくエラーにする。書き出しのたびに自分を捨てる集計を頼む人はいないし、
全消去には `--key-frequency-reset` がある。

書き出しは「読む→メモリ側をマージ→切り捨て→一時ファイルへ書く→rename」で行う。
成功したらメモリ側を空にする。失敗したらメモリに残したまま `false` を返し、次回に持ち越す。

### 9.7 macOSから見えないもの

**これは実装の限界ではなく、この観測点の性質である。** キーボードが送るのはHIDのキーコードで
あって、どの物理キーが押されたかではない。したがって次は原理的に区別できない。

- **分割キーボードで同じキーコードを複数の位置に割り当てた場合。** 例えば Enter を親指の
  実キーと `LALT_T` / `LSFT_T` のような mod-tap の両方に置くと、どのキーで打っても
  同じキーコードが届く。**同じ合計値を各キーに表示し、共有であることを `◇` で明示する。**
  頭数で割らない。割ると存在しない精度を発明することになる。
- **レイヤーキーのhold。** `LT1` を押さえてレイヤー1のキーを打つとき、macOSへ届くのは
  レイヤー1側のキーコードだけで、`LT1` を押したこと自体は届かない。ファームウェア内で完結する。
  数えられるのはtap動作だけである。
- **ロータリーエンコーダの回転と押下、メディアキー。** system-defined イベントで届くため
  keyDown を見ている event tap には来ない。
- **キーボードが送るマウスイベント。** `KC_BTN1` などはマウスイベントとして届く。

図ではこれらを「押されていない」ではなく「数えられない」として、破線と注記で描き分ける。
冷たい色のキーが「使っていない」のか「見えていない」のかが区別できないと、図そのものが嘘になる。

#### 9.7.1 `kCGEventFlagMaskSecondaryFn` は修飾キーの記録ではない

名前に反して、これは「ユーザーが `fn` を押していた」という記録ではない。
`CGEventTypes.h` はこのビットを「Special key identifiers」の側に置いており、macOS は
**ファンクションキー群**——矢印4つ、Home、End、Page Up、Page Down、forward Delete、Help、
F1以降——のイベントすべてに、`fn` に触れたかどうかと無関係に立てる。

当初はこれを Command / Control / Option と同じ「数えないフラグ」に入れていた。結果として
**矢印キーが原理的に一度も数えられず**、しかも図の上では通常キーとして描かれていたため、
「一度も押していない」と読める冷たいキーになっていた。**実際は「一度も数えていない」である。**
これは9.7が禁じている種類の嘘そのものなので、このフラグを除外集合から外した。

代償として、本当に `fn` を押しながらの打鍵はそのキーとして数えられる。両者を区別するビットは
無く、ナビゲーションキー6つを丸ごと取りこぼすほうが大きな誤りだと判断した。

この挙動は当初Appleのヘッダの分類とドキュメント記述に基づく判断だったが、2026-08-28の
実機トライアルで矢印4キーすべてが計数されることを確認し、修正の効果は実測済みになった
（[verification.md](./verification.md)）。

#### 9.7.2 Shiftラップと物理Shiftキーの分離

`LSFT(KC_ENTER)` のようなラップキーをタップすると、ファームウェアが Shift down → キー down →
キー up → Shift up を送る。これは**人がShiftを押しながら打ったときとイベント列が同一**で、
どのビットにも区別が残らない。したがってソフトウェア側だけでは分離できない。タイミング閾値で
推測する案は検討したが、USBのジッタに依存する確率的な答えしか出ず、「疑わしきは数えない」の
方針に反するため不採用とした。

分離はキーマップ側で行える。macOSは左右のShiftを別の仮想キーコード（0x38 / 0x3C）で報告する
ので、**ラップを物理Shiftキーと反対の手に置けば**、物理キーの計数とラップ由来の計数が
キーコードの段階で分かれる。2026-08-28に実際のキーマップで `LSFT(KC_ENTER)` の1つを
`RSFT(KC_ENTER)` へ変更した。変換への影響はない（WKRは左右を区別しない `maskShift` を見る）。

図の側は、キーマップにShiftラップがあることを検出して側ごとの注記を自動で出す。
左ラップは「左Shiftの計数に混入している」、右ラップは「右Shiftの計数はラップの回数の目安」
という反対の意味になるためで、読み手に規則を暗記させない。

**検出は全レイヤーを見る。** 図はレイヤーごとのタブに分かれるが、注記が説明する計数は実際に
打った全レイヤーから来る。記号レイヤーが `LSFT(…)` で埋まっていれば、レイヤー0からラップを
一掃しても左Shiftへの混入は続く。表示中のタブだけを見る検出は、まさに混入が見えにくくなった
瞬間に警告を消してしまうので、`.vil` の全レイヤーを走査して側を集める。

#### 9.7.3 tap / hold兼用キーと共有する論理modifier

`.vil` は `LSFT_T(KC_LANG1)` のような兼用キーについて、tap と hold の意味を別々に持っている。
tap は `KC_LANG1`、hold は LShift であり、ホストが観測する識別子も互いに異なる。この2つを
1キャップの識別子配列へ平らにして合算すると、「その物理キーを使った回数」という観測していない
値を作ってしまう。そこでモデルは tap と hold を別の action part として保持し、レポートでは
**上半分を HOLD、下半分を TAP** として、それぞれ独立した回数とヒート色を描く。

専用 `KC_LSHIFT` とすべての `LSFT_T(...)` の hold は、macOS では同じ LShift の仮想キーコード
`0x38` になる。保存データには発生元の物理位置が無いため、位置ごとの回数へ分解できない。
レポートは1つの論理 LShift 合計を専用キーと各 hold 面にそのまま再表示し、共有を `◇` と
ツールチップで示す。**表示箇所の数を掛けず、表示された値同士も足さない。** 全体合計と
ランキングには LShift を1回だけ含め、指別集計でも1回だけ未帰属分へ入れる。

この値は「専用 LShift と各 `LSFT_T` をそれぞれ何回押したか」の内訳ではない。9.7.2の
`LSFT(...)` ラップや、同じMacへ接続された別のキーボードが左Shiftを送れば、それも同じ論理合計に
入る。また同じShiftフラグが既に下がっている間の重複押下は区別できない。

`LT(...)` の hold は対照的にファームウェア内だけで完結し、対応するホスト識別子を持たない。
その場合も上下には分けるが、HOLD面は「数えられない」として描き、TAP面だけに回数を出す。
複数のmodifierを同時にholdするmod-tapも、複数の論理modifier合計から「このholdの1回」へ
戻せないため、単一の回数は表示しない。

#### 9.7.4 指ごとの集計で、どの指にも割り当てないもの

指別の表は「その指が叩いた回数」を答えるものとする。ここから2種類を外す。

- **修飾キー。** 押しっぱなしにするものであり、叩く回数とは性質が違う。混ぜると小指が常に
  最上位になり、通常の配列分析の数字と比較できなくなる。キーごとの数値には出す。
- **複数のキーが送るキーコード。** Corne の Enter のように、どの物理キーで打ったか macOS が
  報告しないものは、**どの指にも割り当てない。**

後者は当初「最初に見つかったキーの指へまとめる」としていた。実際に描いてみると、Enter を
複数のキーに割り当てたキーマップで**全量が左手に寄り、右親指が 0 と表示された。**
右親指は最も酷使されているキーの1つである。0 という露骨な数字が出たのは幸運な側で、
同じ規則はもっと小さい量を見えないところで動かす。どちらの指も稼いでいない数は下段の
「指の割り当てなし」へ入れ、注記でその理由を出す。

### 9.8 UIをHTMLレポートにした理由

常駐プロセスは `LSUIElement` でウィンドウを一切持たない。ヒートマップのためにウィンドウを
出すと、フォーカスを奪って変換の実機確認を妨げる経路が増え、メニューバー常駐UI
（[roadmap.md](./roadmap.md) 2節）の検証項目も先に必要になる。

`--key-frequency-report` は自己完結したHTMLを1枚書いて終了する。TCC権限には触れず、外部への
参照を持たず（フォント・スクリプト・画像すべてインライン）、SVGなのでJIS・US・Cornixの3配列を
同じデータから描き分けられる。レポートの生成に入力監視権限は要らない。自分が書いた集計値を
読むだけの操作で権限を要求すると、権限を外したMacで図が見られなくなる。

### 9.9 Cornixの配列をどこから得るか

Corneの物理配置は固定だが、どのキーコードがどの位置から出るかはユーザーのキーマップ次第である。
`--vil` にVialの `.vil` エクスポートを渡すと、各レイヤーのキートップとtap / holdの意味を読み、
数えられる動作があるレイヤーをタブとして表示する。渡さなければ組み込みの既定配列を描く。
**`.vil` は集計値の発生元を復元するものではなく、保存済みの論理キー合計をどこへ表示するかだけを
決める。** キーマップが読めなくても標準エラーへ1行出して既定配列で続行し、レポートそのものは
必ず出す。

組み込みの既定配列は、QMK crkbd の既定レイヤーに 英数 / かな を Space / Enter の隣へ置いた、
このプロジェクトが定義する汎用配列である。誰かの実キーマップではない。このアプリの変換ゲートは
英数 / かな で切り替わるため、既定の絵にもこの2キーは要る。下段グリッドの6キーは構成による
差が大きいため空白にしてあり、実物の配列は `.vil` で与える。

`.vil` のキーコードは QMK のキーコード空間で符号化されている。文字列トークン（`LT1(KC_SPACE)`、
`LALT_T(KC_ENTER)`）と生の16進（`0xc04`）の両方を解釈する。**もっとも間違えやすいのは
`LSFT(KC_ENTER)` と `LSFT_T(KC_ENTER)` の違いである。** 前者は Shift+Return を送り、後者はtapで
素の Return、holdでLShiftを送る。集計上は別の動作になり、後者は上下に分割して表示する。

生の16進のうち QK_MODS 域（`0x0100`–`0x1FFF`）の値は、修飾ビットと基本キーコードへ分解して
解釈する。例えば `0xc04` は mods `0x0C` = LALT|LGUI、基本キーコード `0x04` = `KC_A`、
すなわち ⌘⌥A である。**これは符号化規則からの導出であって実機で押して確かめたものではない。**
Vial自身がこの種のキーに名前を持たず16進で表示していることとは整合する。Command を含むキーは、
どちらにせよ集計対象外である。

### 9.9.1 SIGTERM では終了処理が走っていなかった

`make stop` は SIGTERM を送るが、**AppKit は SIGTERM にハンドラを入れない。** 既定動作は
プロセスの即時終了で、`applicationWillTerminate` は呼ばれない。この機能が来るまで誰も
依存していなかったが、打鍵頻度は最大120秒ぶんをメモリに持つので、そのまま捨てられる。

2026-08-28に実測した。`make stop` のあと、最終の `key-frequency flush=ok` も
`summary` 行も出ず、集計ファイルの mtime は直前の定期 flush のままだった。

`signal(SIGTERM, SIG_IGN)` で既定動作を外し、`DispatchSource` で同じシグナルを main queue で
受けて `NSApplication.terminate` を呼ぶ。以後は他の終了経路とまったく同じ後始末を通る。
**影響は集計だけではない。** event tap の解放も保留かなの破棄も同様に飛ばされていた。

#### 9.9.2 高位レイヤーのタブ（2026-08-29追加）

当初はレイヤー0だけを描き、「どのレイヤー経由で届いたかを知らないため、高位レイヤーを
描いても数値を対応づけられない」と判断していた。これは**一意性による帰属を見落としていた**。
macOSがレイヤーを報告しないのは変わらないが、あるキーコードが全レイヤーを通して**1箇所にしか
ない**なら、その数値は推測なしにそのキーのものと言える。実際のキーマップでは、レイヤー0に
描かれない識別子46個のうち35個（数字と記号のほぼ全部）がこの条件を満たしていた。

複数箇所にあるもの（矢印、Home/Endなど）は、レイヤー0の重複Enterに使っている既存の
共有表示——各キャップに合算値＋共有マーク——をレイヤーをまたいで適用する。共有判定は
`model` が同じジオメトリ群（ファミリー）全体で行い、指ごとの集計も同じファミリーで
計算するので、どのタブでも同じ答えになる。

高位レイヤーはファイルだけから描き、組み込み既定へはフォールバックしない。高位レイヤーの
空きは「このレイヤーでは何も送らない」という事実であり、レイヤー0の既定で埋めると
ファームウェアに無い刻印を描いてしまう。何も数えられないレイヤーはタブにしない
（Vialはファームウェアの全スロットを書き出すため、実機の `.vil` には空レイヤーが6枚ある）。

実装済み・ユニットテスト済み。2026-08-28に実機トライアルを行い、タイマー flush、
パーミッション、保存形式、矢印・修飾キー・`英数`/`かな` の計数、パスワード欄での不計数を
確認した。2026-08-29に終了時 flush（保留打鍵あり）と日またぎのバケット切り替えも実測した。
2026-08-31にtap / hold分割と共有 LShift 合計を実データから生成したHTMLでブラウザ確認した。
