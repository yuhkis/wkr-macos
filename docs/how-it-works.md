# 動作原理

このドキュメントは「wkr-macos が何をどうやって実現しているのか」を通しで説明します。
インストール手順は [install.md](./install.md)、配列表と綴りの一覧は
[layout-reference.md](./layout-reference.md)、採用／不採用の設計判断と安全境界は
[design.md](./design.md) にあります。

---

## 1. 前提：わから配列とは

[わから配列](https://scrapbox.io/yuhkis/%E3%82%8F%E3%81%8B%E3%82%89%E9%85%8D%E5%88%97)（wkr）は、
ローマ字入力をベースにしたかな入力配列です。左手で子音（行）、右手で母音（段）を打つ左右交互入力で、
`W` `E` `R` と打つと `わから` になります（`W`=わ行、`E`=か行、`R`=ら行。配列名の由来）。

通常のローマ字入力で1打鍵で確定するかなは `あいうえお` の5文字だけですが、わから配列では
`あ い う え お や ゆ よ ん っ ー` の11文字が1打鍵で確定します。さらに子音キー単独でその行の
あ段（`E` → `か`）が確定するため、`か さ た な は ま ら わ が ざ だ ば ぱ ふぁ` も実質1打鍵です。

配列そのものの仕様・意図は上流の [yuhkis/wkr-layout](https://github.com/yuhkis/wkr-layout) が持ちます。

## 2. 解きたい問題

わから配列は「ローマ字テーブルの差し替え」で実現できます。Google 日本語入力には
ローマ字テーブルのインポートがあり、azooKey にはカスタム入力テーブルがあるので、
上流リポジトリはその2形式の表を配布しています。

**しかし macOS 標準のApple日本語入力（Kotoeri）にはローマ字テーブルを差し替える機能がありません。**
かといって Apple日本語入力を捨てると、macOS に統合された変換エンジン・学習・ライブ変換も一緒に失われます。

そこで wkr-macos は、テーブルを差し替えるのではなく、**Apple日本語入力の手前に立って物理キーを翻訳する**
という方針を取ります。

## 3. 基本アイデア：ローマ字への「翻訳」

Apple日本語入力は標準ローマ字を受け取ってかなに変換します。ならば、

- 物理キー `E` `K` を横取りして、
- わから配列の状態機械で `き` だと解釈し、
- **Apple日本語入力に対しては標準ローマ字 `k` `i` を打ったことにする**

とすれば、Apple日本語入力から見れば普通のローマ字入力と区別がつきません。未確定文字列も、
Space による漢字変換候補も、学習も、そのまま生きます。

```text
物理キーボード（JIS）
   │  E, K, W, R, Space, Return …
   ▼
CGEventTap（.cgSessionEventTap / headInsert / active filter）
   │  変換対象のkeyDown/keyUpだけを抑止し、それ以外は素通し
   ▼
WKRCore … AppKit/Core Graphics非依存のTrie（有限状態トランスデューサ）
   │  215件の正規化規則で「物理キー列 → かな／記号」を決める
   ▼
出力アダプタ（3方式のいずれか）
   │  deferred-romaji / prefix-romaji / optimistic-romaji
   ▼
合成キーイベント（標準ローマ字、または一部だけUnicode文字列）
   │  自分が送ったものと分かるようマーカーを付ける
   ▼
Apple日本語入力（Kotoeri）
   ▼
対象アプリの未確定文字列・変換候補
```

### なぜ自前IMEにしないのか

InputMethodKit で自前のIMEを書けば、`setMarkedText` 相当で未確定文字列を完全に制御できます。
ただしその場合、**Apple日本語入力の変換エンジンだけを公開APIで借りることはできません。**
自前IMEにすると「独自IME＋別の変換エンジン」という別プロジェクト級の話になります。
wkr-macos の目的は Apple日本語入力を置き換えることではなく、その前段に配列を差し込むことなので、
イベントタップ方式を採っています。

## 4. 変換の中身：曖昧接頭辞のあるTrie

わから配列は「1キーで確定することも、2キー目で別のかなになることもある」配列です。
`E` は単独なら `か` ですが、`E K` なら `き` です。つまり `E` は**曖昧な接頭辞**です。

`WKRCore` はこれを Trie（有限状態トランスデューサ）として持ちます。各ノードは

- `children`: 継続できる物理キー
- `output`: そのノード単独で成立する出力（かな＋送出するローマ字）

を持ち、次の3点が本質です。

1. **未定義の次キーを捨てない。** `E S K` の `S` は `E` の継続ではないので、まず `E → か` を確定させ、
   **同じ `S` をルートから再処理**します。これで `かし` が正しく出ます。キーを取りこぼしません。
2. **境界キーで確定する。** Space / Return / Tab / 句読点が来たら、保留中の出力を先に送ってから
   原キーを通します。押鍵数は増えません。
3. **リセット条件を明示する。** アプリ切替、入力ソース変更、マウスクリック、カーソル移動、Escape、
   修飾キー付き入力では、内部状態を安全に捨てます。

Controlによる変換だけは、変換先で扱いを分けます。キー割当てはApple日本語入力の設定で変わります。
今回報告された割当てでは、`Ctrl+J` / `Ctrl+K` のかな変換は保留中の母音まで送ってから原キーを通し、
`Ctrl+L` / `Ctrl+;` のローマ字変換は母音を補わず、画面に出ている子音までをそのまま変換させます。
deferred-romajiでは同じ仮ローマ字だけを送り、optimistic-romajiでは仮かなを取り消してその状態へ
戻すので、どの方式でも物理入力にない末尾母音を追加しません。他のキー設定とF9 / F10はこの分類の
対象外です。

規則は上流の表を実行時に読むのではなく、`Sources/WKRCore/WKRLayout.swift` に**revision固定の
正規化スナップショット**として215件持っています。上流の記号領域には重複・区切り欠落・制御文字混入が
実在するため、推測で実行時テーブルに入れず `quarantinedUpstreamEntries` に根拠付きで隔離しています。

## 5. 出力方式：どのタイミングで何を送るか

同じTrieを共有したまま、「いつ画面に文字を出すか」だけが違う3方式があります。

| 方式 | `E` を押した瞬間の表示 | Backspaceによる差し替え | 位置づけ |
| --- | --- | --- | --- |
| `deferred-romaji` | 何も出ない（1キー遅延） | 使わない | 最も安全。CLIの既定値 |
| `prefix-romaji` | `k` | 起きる枝を表で固定（66件） | **常用方式。**ログイン時起動はこれ |
| `optimistic-romaji` | `か`（仮のかな） | 規則IDごとの削除プロファイル | 実験用。明示フラグが必要 |

### 5.1 deferred-romaji（安全方式）

曖昧な接頭辞は、継続しない次キーか境界キーが来るまで保留し、確定してから初めてローマ字を送ります。
Backspaceを一切使わないので、外部の未確定文字列を書き換えることがなく、内部状態とアプリの状態がずれません。
欠点は、あ段の表示が原則1キー遅れることです。

### 5.2 optimistic-romaji（即時方式・実験）

曖昧ノードの単独出力を即座に送り（`E` で `ka` → `か` と表示）、継続キーが来たら
Backspaceで消して送り直します（`K` で `き` へ差し替え）。即時表示は得られますが、
削除の単位がIMEと対象アプリの状態に依存します。`E` / `EK` の1回削除は TextEdit・Notes・Safari で
成立していますが全行は未実測のため、`--allow-unverified-optimistic` がない起動は拒否します。

### 5.3 prefix-romaji（ちらつき抑制方式・常用）

**1キー目から必ず表示を出し、取り消しが必要な枝を既知の66件に限定する**方式です。これが常用方式です。

考え方は「そのノードから到達し得る全出力が共有しているローマ字だけを先に流す」ことです。

1. `E` を押す → か行の全出力 `ka`/`ki`/`ku`/`ke`/`ko`/`kya`/`kyu`/`kyo` が共有する `k` だけを送る。
   画面は `k`。ローマ字入力をしているときの見え方そのものです。
2. `K` を押す → `EK → き` が確定するので残りの `i` を送る。画面は `き`。
3. `E` の次に `R` → 先に `E` の残り `a` を送って `か` を確定させ、続けてら行の共有接頭辞 `r` を送る。
   画面は `かr`。
4. Enter → 保留中の `a` を先に送ってから Enter を通す。押鍵数は変わらず `わから` が確定します。

流す量は、Trieの各ノードについて次の順で事前計算します。

1. 共有接頭辞が空でなければ、その**1文字目**を流す。全枝を保護できるので取り消しが起きません。
2. 共有接頭辞が空でも、同じ1文字目で始まる出力が他にもあれば1文字目を流す。
   `X` 行の `ふぁ`/`ふぃ`/`ふゅ`/`ふぇ`/`ふぉ` は `f` を共有するので、`X` は `f` を流します。
3. その1文字目で始まる出力が自分だけなら、**自ノードの出力を全部流す**。1文字だけでは何も保護できず
   かなも表示されないためです。これが `H → あ` と同じ即時表示を `U → や` でも得る規則です。

ローマ字を1つも持たない `Y` 記号レイヤーだけは、仮表示用の1文字（`y`）を明示的に与えています。
確定文字である `■` などを仮表示に使わないのは、記号が決まる前に本文を書き換えることになるからです。

**取り消しが起きるのは66件だけで、テストで集合として固定しています**（想定外の規則が取り消しを
始めるとテストが落ちます）。内訳は `X` 行の `てぃ`/`てゅ`/`でぃ`/`でゅ` 4件、
行の1文字目を継がない出力6件、`Y` 記号レイヤー55件です。削除数は**表示されている単位**で数えます。
`k` のような未合成のローマ字は1文字が1単位、`や` のように送出2文字がすでに1かなに合成されている
場合も1単位なので、どちらもBackspace 1回です。

この方式のために、行内で1文字目が割れていた綴りを訓令式へ揃えています
（`ち`=`ti`、`ふ`=`hu`、`じ`=`zi` など）。詳細と全一覧は
[layout-reference.md](./layout-reference.md) にあります。**かな自体は上流と同一で、
変わっているのは送出するローマ字列だけです。**

## 6. Unicode直接注入（特殊かな・記号のみ）

通常のかなは、Space変換を維持するために必ず標準ローマ字で送ります。
ただし Apple日本語入力で一意なローマ字表現を保証しにくい `ヶ` / `ヴ` / `ゐ` / `ゑ` / `ゎ` と、
記号58件を `CGEvent.keyboardSetUnicodeString` によるマーカー付きイベントで送ります。
**この経路は未確定文字列があると届かないため、そのときは送らずログに残します**（2026-08-16 実測、
[verification.md](./verification.md)）。矢印4件と `ヶ` `ゐ` `ゑ` `ゎ` はことえりのローマ字表にある綴りで
送るので、この制約を受けません。

Unicodeイベントはその場で確定してしまうため、この経路は最小限に留めています。
Space変換を残したい `「` / `」` / `『` / `』` の JIS括弧キーは、Apple日本語入力自身が同じ文字を
未確定文字列として出せるので、**横取りせずそのまま通します**（`WKRLayout.passThroughKeys`）。
`（` や `＜` と同じ変換体験に揃えるためです。

## 7. 英字への打ち直し

日本語入力モードのまま英単語を打ってしまったとき、Apple日本語入力には `英数` キーの連打で
入力中の文字を英字へ戻す機能があります。ところが WKR 経由では、**戻ってくるのは物理キー列ではなく
WKR が送った標準ローマ字**です。`thing` のつもりで打った `T` `H` `I` `N` `G` は `layunnh` になります。
Apple日本語入力が保持しているのは受け取ったローマ字の生列で、物理キー列を知っているのは
WKR だけだからです。

そこで、**`英数` を素早く2回叩くと、打った物理キーどおりの英字へ置き換えます。**

```text
T H I N G  と打つ        画面は「ぁゆんh」（WKRは la yu nn h の7文字を送っている）
   │
   ▼
英数 を素早く2回          Apple日本語入力が読み戻して「layunnh」
   │
   ▼
連打が止まって0.25秒       WKR が7文字ぶん Backspace を送り、`thing` を入れる
```

WKR は**連打の回数を数えません。** 読み戻しに必要な押下回数はアプリや未確定文字列の状態によって
変わるので、固定回数で発火すると、まだアルファベットが出ていない画面に Backspace を送りかねません。
連打が止まったことだけを合図にすれば、利用者はそのアプリに必要なだけ叩けば済みます。
`英数` 1回は通常のモード切替のままで、何も起きません。

置き換えられるのは、**WKR が自分で送ったローマ字ちょうど**です。そのために未確定スコープの物理キー列と
送出済みローマ字の文字数をプロセス内だけで保持し、上限12打鍵と寿命を付けています。整合が取れない
条件では何もしません。Space変換を挟んだ、Backspaceを押した、記号のようにUnicodeを注入する
起きる枝を通った、上限を超えた、といった場合です。判断の根拠と全条件は
[design.md](./design.md) の「8. 英字への打ち直し」にあります。

トリガは `--english-fallback` かユーザーデフォルト `EnglishFallbackTrigger` で変更できます
（`eisu+eisu` / `eisu+return` / `eisu+tab` / `off`）。使い方は [install.md](./install.md) にあります。

## 8. 安全ゲートとプライバシー

このアプリは「入力監視」と「イベント送信」の権限を要求します。だからこそ、変換しない条件を
広く取り、異常時は必ず通常入力に戻ることを優先しています。

**変換を行わない条件（いずれか1つでも該当すれば素通し）**

- Input Monitoring / Accessibility 権限が揃っていない
- 現在の入力ソースが、起動時に指定した source ID と mode ID の**両方に完全一致しない**
  （Apple日本語入力らしいIDを推測・前方一致しません）
- 前面アプリが `--exclude-app` で除外されている（仮想マシン・リモートデスクトップ用）
- `IsSecureEventInputEnabled()` が真（パスワード欄など）
- Command / Control / Option / Caps Lock / Fn を含む入力
- event tap が無効化された、権限が実行中に取り消された、合成イベントの生成に失敗した

最後の3つでは自動再有効化せず、**fail closed で常駐プロセスごと終了**します。
壊れた状態で動き続けるより、通常入力に戻れることを優先する設計です。

`IsSecureEventInputEnabled()` はフィールド単位ではなく**セッション全体**の状態です。前面が
普通のテキスト欄でも、別のアプリが Secure Event Input を握っていれば真であり続けます。
パスワードマネージャのロック解除ダイアログが開いたまま放置される例が実際にあり、その間は
何も変換されません（[verification.md](./verification.md)）。**止まっていることと、その理由は
メニューバーのアイコンとメニューで分かります。** メニューには保持プロセスのPIDと生死、経過時間、
対処まで出ます。ログは事後の記録として残り、切り分け手順は
[install.md](./install.md#変換が止まったときのログの見方) にあります。

**誰が握っているかで対処が変わる**ため、ログには保持プロセスのPIDと、それがまだ生きているかを
残します。`secure-event-input enabled=true holder-pid=62279 holder=alive` なら、そのアプリを
終了するかダイアログを閉じれば戻ります。`holder=gone` は保持プロセスが終了したのにカウントだけが
残った状態で、アプリの終了も画面ロックも効かず、ログアウト以外に回収手段がありません。
`holder=unknown` は保持者を読めなかった場合で、変換を止める判断自体は
`IsSecureEventInputEnabled()` だけで行うため、読めなくても安全側の挙動は変わりません。
解除時の `held-seconds` は閉じていた秒数で、パスワード欄なら1秒未満、異常なら数百秒以上に
なります（実測は [verification.md](./verification.md)）。

**記録しないもの**

入力文字列、クリップボード、変換候補は、ログにもファイルにもネットワークにも出しません。
そもそもネットワーク機能を持ちません。ログに出るのは権限状態、モード、入力ソースID、
状態コード、エラー種別、集計件数、変換ゲートが閉じていた秒数、Secure Event Input の
保持プロセスID（数値と生死だけ。プロセス名やパスは出しません）だけです。

英字への打ち直し（7節）だけは、未確定文字列の範囲の物理キー列を**プロセスのメモリ内に**
保持します。上限12打鍵と寿命があり、確定・アプリ切替・マウスクリック・Secure Event Input などで
破棄します。ファイル・標準出力・ログ・ネットワークへは出しません。ログに出るのは
`english-fallback state=replaced keys=5` のように、状態と打鍵数だけです。

打鍵頻度の記録（9節）を明示的に有効にしたときだけ、キーごとの**累計回数**を暦日単位で
ローカルファイルへ保存します。順序も時刻も入力文字列も保存しません。既定は無効で、
Secure Event Input・権限欠如・除外アプリ・対象外の入力ソースでは1回も数えません。
ログに出るのは `key-frequency flush=ok days=3` のような結果だけです。

`IsSecureEventInputEnabled()` は現行SDKヘッダ上 thread-safe ではないため、event tap の
コールバックからは呼ばず、main run loop の common mode Timer で確認した結果を参照します。
JIS `かな` / `英数` キーとアプリ切替では、通知を待つ前に先に変換ゲートを閉じます。

## 9. 打鍵頻度の記録（任意・既定オフ）

macOS に届いた論理キーをどれだけ使ったかを数え、キーボードの絵の上にヒートマップとして描けます。
**既定では動きません。** `--key-frequency on` で明示的に有効にしたときだけ数えます。

保存するのは `(キーコード, Shiftの有無) → 回数` と**暦日**だけです。打鍵の順序も、暦日より
細かい時刻も、入力文字列も保存しません。順序を落とした度数分布からは入力文字列を復元できません
（`WKR` と `RKW` は同じ集計になります）。アプリケーション名も取りません。

数えない条件は、8節の「変換を行わない条件」とほぼ同じゲートを使います。Secure Event Input、
権限欠如、除外アプリ、対象外の入力ソースでは1回も数えません。**Web のパスワード欄のように
Secure Event Input を立てない入力先があるため、「Apple日本語入力ひらがなが有効な間だけ」という
条件が実質的な防波堤になります。** Command / Control / Option 付きのショートカットと
オートリピートも数えません。

`かな` / `英数` だけは入力ソースの一致を条件から外しています。この2キーは入力ソースを切り替える
キーそのものなので、一致を求めると `かな` が構造的に数えられません。モード切替は打った内容を
何も含まないため、他の条件はそのまま課したうえでこの1点だけ緩めています。

有効時だけ `.flagsChanged` をイベントマスクに加えます。Shift や親指の Command は keyDown では
届かないためです。この経路は観測専用で、常に元イベントをそのまま返します。**無効時の
イベントマスクと1打鍵あたりの処理は、この機能が無かったときと完全に同一です。**

コールバック内でやるのは辞書の1加算だけで、ファイルへの書き出しは120秒ごとと終了時に
main run loop 側で行います。保存先は Application Support 配下（ファイル 0600）で、
**古い分が自動で消えることはありません**（上限が要るときだけ `--key-frequency-retention` で
指定します）。ネットワークへは出ません。

Cornix の `.vil` に tap / hold 兼用キーがある場合、キートップを**上半分の HOLD、下半分の TAP**
に分けます。2つの動作は別々に回数とヒート色を持ち、足して1つの「この物理キーの回数」には
しません。macOS が観測しているのは物理位置ではなく、ファームウェアが解決した後の論理キーだからです。

たとえば専用 `KC_LSHIFT` とすべての `LSFT_T(...)` の hold は、どれも同じ論理 LShift
（仮想キーコード `0x38`）として届きます。レポートは同じ共有合計を各動作に再表示して `◇` を付け、
どの位置から来たかを推定しません。表示箇所が増えても合計を掛けたり足したりせず、全体合計、
ランキング、指別集計の計算にはこの LShift 合計を1回だけ入れます。修飾キーなので特定の指には
割り当てません。

**macOS から見えないものがあります。** キーボードが送るのは HID のキーコードであって、
どの物理キーが押されたかではありません。分割キーボードで Enter を3か所に割り当てていれば、
どれが押されたかは区別できないので合算値を各キーに表示し、共有であることを図上で示します。
`LT(...)` などレイヤーキーの hold はファームウェア内で完結して届かず、エンコーダとメディアキーは
system-defined イベントなので keyDown を見ているこの event tap には来ません。
図ではこれらを「押されていない」ではなく「数えられない」として描き分けます。

手順は [install.md](./install.md#打鍵頻度の記録とヒートマップ)、設計判断は
[design.md](./design.md) の9節にあります。

## 10. 既知の限界

- **JISキーボード専用。** 物理キーの正規化がJIS配列を前提にしています。
  ヒートマップは JIS・US・Cornix の3配列で描き分けられますが、**変換そのものは JIS 専用**です。
  US配列やCorne系分割キーボードでも、macOS へ JIS のキーコードが届いていれば変換は成立します。
- **Apple日本語入力の「ローマ字入力」「ひらがな」専用。** それ以外の入力ソースでは完全に素通しします。
- **`英数` キーの読み戻しは物理キー列ではなく WKR が送った標準ローマ字を返します。**
  `英数` を素早く2回叩けば打ったとおりの英字へ置き換えますが（7節）、これは Unicode 直接注入を
  使うため、そのイベントを無視するアプリでは働きません。2026-08-15 に TextEdit と Claude.app で
  確認済みです。**連打の間隔が Apple日本語入力の2回押し判定とずれた場合の挙動は未確認です。**
  確認範囲は [verification.md](./verification.md) にあります。
- **実機確認の範囲は限定的です。** かな全行・訓令式綴り・Unicode経路・取り消し枝の代表列は
  TextEdit で確認済みです。`E` / `EK` の基本動作は TextEdit・Notes・Safari・ChatGPT入力欄で
  確認しています。**記号レイヤーは2026-08-13に実機確認済みですが、アプリ別の網羅的な
  互換性確認は未完了です。**
- **Unicodeイベントを無視するアプリがあり得ます。** 特殊かな・記号はアプリ別の確認対象です。
- **打鍵頻度は「どの物理キーを押したか」ではなく「どのキーコードが届いたか」を数えています。**
  分割キーボードで Enter を3か所に割り当てていれば区別できません。専用 LShift と
  `LSFT_T(...)` の hold も1つの論理 LShift 合計を共有し、位置ごとの内訳は分かりません。
  `LT(...)` などレイヤーキーの hold とエンコーダは届きません。9節と
  [install.md](./install.md#打鍵頻度の記録とヒートマップ) を参照してください。
- **Terminal、VS Code、Slack、Discord、Notion で確認済みです。** VS Code は隠し `textarea`、
  Slack・Discord・Notion は `contenteditable` と、Electron 系の主要な2経路の両方で成立しています。
  ただし網羅的な確認ではないので、未確認のアプリが残っている前提でお使いください。
- **仮想マシンやリモートデスクトップでの挙動は、仮想化ソフトの入力取得階層に依存します。**
  WKRの抑止と合成イベントがゲストへ届くなら、ゲスト側のIMEが標準ローマ字を変換するので
  ゲストに配列を入れる必要はありません。届かない場合や原キーと二重に届く場合は
  `--exclude-app` で除外します。既定の除外リストは持ちません（未検証のBundle IDを
  推測で入れないため）。判定手順は [install.md](./install.md) にあります。
- **上流の表で唯一未実装なのは `■'` → `'` と `■"` → `"` の2件です。**
  この2つはANSI配列での Shift+7 / Shift+2 を指しますが、JISでは同じ物理キーを
  `■&` → `￡` と `■@` → `▼`（azooKey の `’` / `”`）が既に使っています。
  両立できないため実装せず、`quarantinedUpstreamEntries` に理由付きで記録しています。
- **メニューバー表示は状態と停止理由までです。** 変換中・待機中・停止中と、その理由（Secure Event
  Input、対象外の入力ソース、除外アプリ）を示し、メニューから終了できます。ただし上の6条件のうち
  最後の3つ（tap無効化、実行中の権限取り消し、合成イベント生成失敗）は**fail closedでプロセスごと
  終了する**ため表示できません。その場合はアイコンが消えることが唯一の合図です。読み方は
  [install.md](./install.md) にあります。

公開可能な検証結果と確認範囲は [verification.md](./verification.md) にあります。
