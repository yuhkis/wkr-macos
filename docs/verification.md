## 2026-08-14 — `英数` キー連打の読み戻しとEscapeの実挙動

### `英数` キー連打は物理キー列ではなく合成ローマ字を返す

Apple日本語入力には、未確定文字列がある状態で `英数` キーを連打すると入力中の文字を英字へ戻す機能が
あります。WKR経由では、この読み戻しが**物理キー列ではなくWKRが送った標準ローマ字**を返します。

- 入力ソース: Apple日本語入力「ローマ字入力」「ひらがな」、prefix-romaji。
- 操作: 物理キー `T` `H` `I` `N` `G` を打ってから `英数` を連打する。
- 利用者の意図: `thing`
- 実測値: どちらのアプリでも `layunnh`
  - Claude.app（Electron系、`contenteditable` の入力欄）: 2回押しで `layunnh`。
  - TextEdit: 2回押しでは未確定文字列が消え、3回目で `layunnh` が現れました。

実測値は `TH → ぁ`（`la`）、`I → ゆ`（`yu`）、`N → ん`（`nn`）、`G` のは行共有接頭辞（`h`）を
連結した文字列と一致します。Apple日本語入力は受け取ったローマ字の生列を保持しているため、
WKRの合成イベントがそのまま返るのは仕様どおりの動作です。物理キー列を知っているのはWKRだけで、
Apple日本語入力側に復元の材料はありません。

判定: 読み戻しの内容が合成ローマ字になることは、方式に由来する既知の限界です。WKRが未確定スコープの
物理キー列を保持しない限り復元できません。対策は未着手で、採否も決めていません。
**必要な押下回数はアプリまたは未確定文字列の状態によって変わります**（下記の未確認事項）。

### Escapeの結果はアプリによって異なる

- 入力ソース: Apple日本語入力「ローマ字入力」「ひらがな」、prefix-romaji。
- 操作: 未確定文字列がある状態でEscapeを押す。
- 実測値:
  - TextEdit: 1回目で直前に変換された文節がひらがなへ戻り、2回目で未確定文字列の全体がひらがなへ
    戻り、3回目で未確定文字列が消えました。**段階的な取り消しとして働きます。**
  - Claude.app: 未確定文字列は削除されず、そのまま確定しました。Electron系の `contenteditable` は
    アプリ側がEscapeを処理し得る経路なので、IMEへ届いていない可能性があります。

「WKRはEscapeで合成イベントを送らず、内部状態だけを破棄する」という既存の方針は変えません。
取り消しが段階的で、しかもアプリによって結果が変わる以上、WKRが独自の削除を足すと素のローマ字入力との
食い違いがむしろ大きくなるためです。

### 未確認事項

- Escapeと `英数` 連打のどちらも、必要な押下回数がアプリ依存なのか、未確定文字列の状態
  （ライブ変換がどこまで進んでいるか、保留中のローマ字があるか）依存なのかを切り分けていません。
  **未確定文字列を確実に取り消す手段は、現時点で確立していません。**
- 確認したのはTextEditとClaude.appのみです。Notes、Safariでの再現は未了です。
- ライブ変換の有効・無効による差は確認していません。
- `英数` 連打の読み戻しが、Spaceで変換候補を出した後の未確定文字列に対して何を返すかは
  確認していません。
- 合成イベントで送った `英数` の連打を、Apple日本語入力が連打として認識するかは確認していません。
- Claude.appは基本動作の確認済みアプリ一覧へは加えていません。今回の確認は未確定文字列の生成と
  `英数` 連打・Escapeの結果までで、Space変換、Enter確定、Backspace、カーソル移動、
  アプリ切替後の状態を確認していないためです。

## 2026-08-14 — Secure Event Input による約30分の変換停止

### 症状と実測

常駐したまま約30分にわたり変換が起きず、全キーが素通しになりました。その後、こちらから何も
操作しないうちに復帰しました。

- 入力ソース: Apple日本語入力「ローマ字入力」「ひらがな」、prefix-romaji。
- アプリのログ（`subsystem == "io.github.yuhkis.wkr-macos"`）に残っていたのは次の2件だけです。
  - `secure-event-input enabled=true`
  - その約29分56秒後の `secure-event-input enabled=false`
- 同じ常駐プロセスの稼働期間（約22時間）を通して、`event-tap-disabled`、`conversion-stopped`、
  `permissions` の変化はありませんでした。プロセスは再起動しておらず、権限もevent tapも
  失われていません。

判定: `IsSecureEventInputEnabled()` が真の間は素通しするという既存の安全ゲートが、設計どおりに
働いた結果です。実装の不具合ではありません。

### Secure Event Input を保持していたプロセス（推定）

macOSは Secure Event Input の保持プロセスをログに出しません。ただし、システムログの前後関係は
両端で一致します。

- 有効化の0.3秒前に、パスワードマネージャがロック解除用のパネルを表示し、
  `LocalAuthentication` で Apple Watch と Touch ID の可否を確認しています。
- 無効化の1.0秒前に、同じアプリが再び `evaluatePolicy` を実行し、Touch ID の照合が成立しています。

ここから、**ロック解除ダイアログが開いたまま約30分放置され、Touch IDで解除した時点で解放された**
と推定します。直接の証拠ではないため、断定はしていません。

### この症状の一般形

Secure Event Input はフィールド単位ではなく**セッション全体**に効きます。前面のパスワード欄に
限らず、次のような状態でも変換は止まります。

- パスワードマネージャのロック解除ダイアログが開いたままになっている
- ターミナルの Secure Keyboard Entry が有効になっている
- 認証ダイアログが背後に残っている

メニューバー表示が未実装のため、止まっていることを画面から知る手段がありません
（[roadmap.md](./roadmap.md)）。切り分けにはログを見る必要があります。手順は
[install.md](./install.md#変換が止まったときのログの見方) にあります。

### 付随して判明: zshでは `log` がビルトインと衝突する

切り分けの過程で、ドキュメントに載せていた `log stream ...` がmacOSの既定シェルであるzshでは
実行できないことが分かりました。zshには引数を取らない `log` ビルトインがあり、
`zsh:log:1: too many arguments` で失敗します。同じコマンドをbashとfishで実行すると成功します
（3シェルとも実測）。[install.md](./install.md) のコマンドは `/usr/bin/log` へ直しました。

### 未確認事項

- 保持プロセスの特定は、時刻の一致による推定です。保持者を返す公開APIは確認していません。
- `ioreg -l -w 0 | grep -i SecureInput` が `kCGSSessionSecureInputPID` として保持PIDを返すかは、
  この環境では未確認です。症状が解消した後に実行したため、該当キーは出力されませんでした。
- 同じダイアログを開いたときに必ず再現するかは確認していません。
- 約30分という長さが、ダイアログの放置時間そのものなのか、パスワードマネージャ側の自動ロック
  間隔と一致した偶然なのかは切り分けていません。
- 保留中のローマ字がある状態で Secure Event Input が有効になった場合に、送出済みローマ字が
  未確定文字列に取り残されるかは確認していません（今回はreset系のログが出ていないため、
  保留のない状態で有効化されたと考えられます）。

## 2026-08-14 — `英数` 連打の読み戻しが対象とする範囲

同日の [`英数` キー連打の読み戻し](#2026-08-14--英数-キー連打の読み戻しとescapeの実挙動)の続きです。
長めの文で確認しました。

- 入力ソース: Apple日本語入力「ローマ字入力」「ひらがな」、prefix-romaji。
- 操作: 長めの文を入力した状態で `英数` を連打する。
- 実測値: **まだ変換が確定していない部分だけがローマ字のアルファベットへ戻ります。**
  既に確定した部分はかな漢字のまま残ります。
- 追加の実測: Space、Enter、句読点を一度も押さずに「きょうはいいてんきですね」程度の長さを
  打った場合、未確定文字列は分割されず、**部分確定は起きませんでした。**

判定: 画面に現れるアルファベットの長さは「WKRが送出したローマ字の総文字数」ではなく、
**「最後の確定以降に送ったローマ字の文字数」**です。[design.md](./design.md) の
「8. 英字への打ち直し」は送出済み文字数ぶんBackspaceを送る前提だったため、そのままでは
確定済みの本文を削ります。

ただし追加の実測により、**この長さの範囲では確定の境界がSpace・Enter・句読点でしか生まれない**
ことが分かりました。これらはいずれもWKRが観測できるキーで、既存のreset条件に入っています。
そこで文字数を0へ戻せば整合するため、design.md の同節は方式を変えず、上限とfail closedの
条件を足す形で修正しました。

### 未確認事項

- **「きょうはいいてんきですね」を超える長さでの部分確定は確認していません。** より長い未確定
  文字列でライブ変換がキー操作なしに部分確定するのであれば、WKRに境界を知る手段はありません。
  design.md 8.4 の上限をこの実測済みの長さ以下に置くことで、未確認の領域へ入らないようにします。
- 文節数、ライブ変換の有効・無効による差は確認していません。

## 2026-08-15 — 英字への打ち直しの実機確認

`feature/english-fallback-chord` のビルドを `/Applications` へ配備し、prefix-romaji、
Apple日本語入力「ローマ字入力」「ひらがな」で確認しました。

### コード方式（`英数` を押しながら Enter）

- 対象アプリ: TextEdit と Claude.app（下記の未確認事項を参照）
- 操作: `T` `H` `I` `N` `G` → `英数` 連打 → `英数` を押したまま Enter
- 実測値: `layunnh` が `thing` へ置き換わりました（`english-fallback state=replaced keys=5`）。

置き換え自体は成立しましたが、**操作としては成立しませんでした。** Enterを押す時点で `英数` が
既に離れていることが多く、その場合コードとして判定されません。押しっぱなしを要求する設計に
無理がありました。既定から外し、選択肢としてのみ残しています。

### 連打方式（`英数` を素早く2回、現在の既定）

- 対象アプリ: TextEdit と Claude.app
- 操作: `T` `H` `I` `N` `G` → `英数` を素早く2回で止める
- 実測値: どちらでも `thing` へ置き換わりました。`english-fallback state=replaced` を
  8件記録しています。

### 先行するテキストがある状態での確認

空の文書では、Backspaceが多すぎても削るものが無いため結果が正しく見えてしまいます。
先にテキストを置いて切り分けました。

- 対象アプリ: TextEdit
- 操作: 英数モードで `ABCDEFGHIJ` を入力 → `かな` → `T` `H` `I` `N` `G` → `英数` を素早く2回で止める
- 期待値: `ABCDEFGHIJthing` なら送出済みローマ字だけを消している。`ABCthing` なら先行7文字を削っている
- 実測値: **`ABCDEFGHIJthing`**

先行するテキストは削られませんでした。2回で止めた時点で、画面には送出済みローマ字がそのまま

### 未解決: 2026-08-14 の観測との差

2026-08-14には、TextEditで `英数` 2回では未確定文字列が消え、アルファベットは3回目で現れると
記録しました。今回は2回で正しく置き換わっています。未確定文字列の内容やライブ変換の進み具合が

未確認のままです。**

ただし連打方式は押下回数を数えず、連打が止まったことだけを合図にします。この差がどちらであっても
動作は変わりません。それがこの方式を選んだ理由でもあります。

## 2026-08-16 — 未確定文字列があると Unicode 直接注入が届かない

`Y` 記号レイヤーが文の途中で入らない、という報告から切り分けました。TextEdit、
Apple日本語入力「ローマ字入力」「ひらがな」、ライブ変換は有効です。

### 症状

| # | 操作 | 実測値 |
| --- | --- | --- |
| A | 未確定なしで `Y` `J` | `↓` が**確定**で表示される |
| B | `H`（あ）を出してから `Y` `J` | 「あ」が未確定のまま。`↓` は出ない |
| C | `W` `E` `R` の後に `Y` `J` | 「和から」が未確定のまま。`↓` は出ない |
| D | `Y` だけ押して Backspace | 仮表示の `y` は消える |
| E | 未確定ありで `T` `,` | C と同じ。`，` は出ない |

**未確定文字列があると、Unicode 直接注入のイベントは黙って捨てられます。** 1打鍵が
画面上は何も起こさずに失われます。E から、`Y` レイヤー59件だけでなく **Unicode 出力67件
全体**（特殊かな5件、`T` 句読点3件を含む）の制約だと分かります。

B で「あ」が「ああ」にならなかったことから、注入イベントの仮想キーコード `0`
（`kVK_ANSI_A`）が `a` として解釈されているのではなく、**イベントごと捨てられている**
ことが分かります。

### 直前の Backspace は原因ではありません

prefix モードでは、Unicode 出力の直前に必ず仮表示を消す Backspace が入ります
（`Y` なら `y`、`E` なら `k`、`T` なら `l`）。deferred モードならこの Backspace が
付かないので、そこで切り分けました。

- 操作: `--mode deferred` で `W` `E` `R` `Y` `J`
- 実測値: 「和から」が未確定のまま。`↓` は出ない

**Backspace との競合ではなく、未確定文字列があること自体が原因です。** 合成イベントの
投入タイミングを分ける対策は成立しません。

### 仮想キーコードを変えると、未確定がなくても届かなくなる

Apple日本語入力が `kVK_ANSI_A` のイベントを自分のキーとして掴んで捨てているなら、
掴まないキーコードなら素通しするのではないか、という仮説を試しました。

- 操作: 注入イベントの仮想キーコードを `105`（`kVK_F13`）にして `W` `E` `R` `Y` `J`
- 実測値: 未確定ありでも**未確定なしでも** `↓` が出ない

**この経路は、Apple日本語入力が `kVK_ANSI_A` のイベントを処理してくれることに完全に
依存しています。** アプリへ直接届ける道はなく、CGEvent 層での回避策はありません。
仮説は否定されたので、実験用に作った `--unicode-keycode` フラグは破棄しました。

### `かな` キーは確定手段に使えません

注入前に未確定文字列を確定させる手段として調べました。

- 未確定文字列がある状態で `かな`: **何も起きません**（確定しません）
- 未確定文字列がない状態で `かな`: **再変換が走ります**

両方向とも不適格です。確定しないので目的を果たさず、しかも未確定がないと判断を誤った
場合に周囲の確定済みテキストを再変換対象にします。**`かな` を合成イベントで送っては
いけません。** 残る確定手段は Return だけですが、ライブ変換が有効な場合はその推測を
確定させることになります。

### 判定

- Unicode 直接注入は「未確定文字列がないときにだけ届き、その場で確定する」経路です。
  未確定文字列に載せることはできません。
- したがって `英数` 連打の読み戻しは記号に届きません。記号を打った時点で確定テキストに
  なるためで、[design.md](./design.md) 8.6 の fail closed 条件どおりです。
- 対策は [design.md](./design.md) 5.4 と 5.6 にあります。

### 未確認事項

- Return で確定した直後の注入が届くかどうかは未確認です。
- ことえりのローマ字表に `zh` / `zj` / `zk` / `zl` → `←↓↑→` のような記号エントリが
  あるかは未確認です。あれば矢印4件はローマ字経路へ移せます。
- ライブ変換を無効にした場合の差は確認していません。
- TextEdit 以外での再現は未了です。

## 2026-08-16 — 同じBundle IDの別ビルドに許可を与えると、配備済みappの権限が外れる

## 2026-08-16 — ad-hoc署名をやめると権限の再許可が要らなくなる

再ビルドのたびに入力監視とアクセシビリティを許可し直す必要があった件です。原因は
designated requirement にありました。

| 署名 | designated requirement |
| --- | --- |
| ad-hoc | `cdhash H"…"` |
| 自己署名のコード署名証明書 | `identifier "io.github.yuhkis.wkr-macos" and certificate leaf = H"…"` |

**ad-hoc はバイナリのハッシュを同一性の条件にしている**ため、1行変えるだけで TCC からは
別のアプリになります。証明書で署名すると条件が Bundle ID と証明書だけになり、バイナリ由来の
項目が消えます。実際、同じ証明書で署名した別々のバイナリ（旧ビルドの再署名と新規ビルド）で
requirement は同一でした。

キーチェーンアクセスの証明書アシスタントで作った自己署名のコード署名証明書を使いました。
Apple Developer Program は不要です。`security find-identity -v -p codesigning` には
`CSSMERR_TP_NOT_TRUSTED` として現れず有効一覧から外れますが、**`codesign` は問題なく使え、
`--options runtime --timestamp` も通り、`codesign --verify --deep --strict` も成功します。**
信頼設定の変更は不要でした。

`--key-frequency-report` でHTMLを生成し、ブラウザで表示を確認しました。

- 外部参照はSVGの名前空間URIだけで、フォント・スクリプト・画像・スタイルはすべてインラインでした。
  ネットワークへ取りに行くものはありません。
- 期間切り替え（全期間／直近7日／直近30日／単日）、3配列のタブ、上位25キーのランキング、
  指別集計、注記の表示が動作しました。単日を選ぶと集計が切り替わることを確認しました。
- ライト／ダーク両方で描画を確認しました。横スクロールは発生しませんでした。
- キートップの文字がキーの矩形からはみ出していないことを、描画後の bbox を全キーについて
  比較して確認しました（超過0件）。
- `.vil` の右手側は外側→内側の順で格納されているため、描画時に反転が要ります。
  反転が抜けると `Y` が右小指に来るので、その位置関係をテストで固定しました。

### 実装中に見つけて直した5件

いずれも図が黙って嘘をつく種類の誤りです。前半2件は実際に描いて見るまで、後半3件は
生成したデータと図を突き合わせるまで気づきませんでした。

- **注記付きのキーの数値が消えていた。** 「集計対象外」という注記があるキーを一律で無地に
  描いていたため、レイヤータップの下にある Space・英数・Backspace や修飾キーが
  すべて空欄になっていました。**これらは盤面で最も打鍵数の多いキーを含みます。**
  注記は「どうやって数えたか」の但し書きであって「数えられない」ではないので、
  数値の有無は識別子を持つかどうかで判定するよう分けました。
- **修飾キー付きのカスタムキー（QK_MODS）が内側の基本キーの打鍵数を表示していた。**
  修飾キー付きキーに内側のキーコードを持たせていたためです。Command / Control / Option 付きの
  イベントは数えないので、そのキーコードに記録されている打鍵はすべて**盤面の別の場所にある
  素のキー**のものでした。修飾キー付きのキーは識別子を持たないよう変更しました。
- **矢印キーが原理的に一度も数えられなかった。** `kCGEventFlagMaskSecondaryFn` を
  Command / Control / Option と同じ「数えないフラグ」に入れていたためです。このビットは
  `fn` の押下記録ではなく、macOS が**ファンクションキー群**（矢印4つ、Home、End、Page Up、
  Page Down、forward Delete、F1以降）のイベントすべてに立てる識別子です。
  結果として矢印は通常キーとして描かれながら常に0で、「一度も押していない」と読めていました。
  除外集合から外しました。**この挙動はAppleのヘッダの分類に基づく判断で、実測ではありません。**
- **Shift 付き打鍵がどこにも描かれていなかった。** キーマップの記述どおり
  Shift なしの識別子だけを持たせていたためですが、Shift は物理的な事実であって
  キーマップの項目ではありません。同じ `A` キーが Shift を押しながらなら Shift 付きを送ります。
  記号レイヤーの `Shift+;` や `Shift+/` が記録だけされて描かれない状態でした。
- **指別集計で右親指が 0 と表示されていた。** 複数のキーが送るキーコード（Enter を複数キーに
  割り当てた場合など）を「最初に見つかったキーの指」へ寄せていたためで、
  全量が左手に落ちていました。**露骨な 0 が出たのは幸運な側で、同じ規則はもっと小さい量を
  見えないところで動かします。** どの指も稼いでいない数は「指の割り当てなし」へ入れ、
  注記で理由を出すように変更しました。

### 図に描かれないキーの確認

生成した集計に含まれるキーコードのうち、各配列の図に現れないものを機械的に突き合わせました。

| 配列 | 描かれないキー | 判定 |
| --- | --- | --- |
| JIS | なし | OK: 全キーが図の上にある |
| US (ANSI) | 英数 (0x66)、かな (0x68) | 仕様: ANSI配列に無いキー。注記済み |
| Cornix | 検証に使ったキーマップのレイヤー0に無いキー | 仕様: レイヤー0に無いキーは描かれない。注記済み |

配列間で差が出る分は、指別集計の「指の割り当てなし・この図に無いキー」行に入ります。
Cornix では 15.8% でした。

### 未確認事項

- **常駐状態での長期記録は未確認です。** 集計の読み出し・レポート生成・リセットは実測しましたが、
  `flush()` が実際にファイルへ書く経路（120秒タイマーと終了時）は実機で走らせていません。
- **flags-changed 経由の修飾キー計数は未確認です。** 押下エッジの判定、左右同時押しで1回になること、
  Caps Lock が点灯側だけ数えられることは、いずれもコード上の設計であって実測ではありません。
- **`kCGEventFlagMaskSecondaryFn` が矢印キーに立つことは実測していません。** Appleのヘッダが
  このビットを「Special key identifiers」に分類していることと、`NSEventModifierFlagFunction` の
  記述に基づく判断です。実機で矢印を押して確かめるのが確実です。
- 日をまたぐセッションでバケットが切り替わることは未確認です。
- 生の16進で書かれた QK_MODS 域のカスタムキーを修飾ビットと基本キーコードへ分解する解釈は、
  QMK のキーコード符号化規則からの導出で、実機で押して確かめたものではありません。Vial 自身が
  この種のキーに名前を持たず16進で表示していることとは整合します。どちらにせよ Command を
  含むものは集計対象外です。

## 2026-08-28 — 打鍵頻度ログの実機トライアル

PR #14（`5cf4c23`）を自己署名証明書で release ビルドして `/Applications` へ配備し、
`--key-frequency on` を付けた prefix モードで起動しました。designated requirement は
配備前後で一致し、**Input Monitoring / Accessibility の再許可なし**で
`permissions listen=true post=true` になりました（2026-08-16 の自己署名運用の再確認）。

打鍵は実機の Corne 系分割キーボードから物理キーで行いました。TextEdit（Apple日本語入力
「ひらがな」）での通常入力、矢印キー、Shift 付き記号、Command 単押し、Safari の
`LocalInputTest.html` パスワード欄への入力、の順です。

### 確認できたこと

| 項目 | 実測 |
| --- | --- |
| 120秒タイマーの flush | `key-frequency flush=ok days=1` が2回、**ちょうど120秒間隔**で記録された |
| 保存先のパーミッション | ディレクトリ 0700、`key-frequency.json` 0600 |
| 保存形式 | `schemaVersion` と暦日バケットのみ。エントリは keyCode / isShifted / count の3フィールドだけで、順序・時刻・文字列は無い。38識別子・計669打鍵 |
| 矢印キーの計数 | ← ↑ ↓ → すべてに数字が付いた。**`kCGEventFlagMaskSecondaryFn` を除外集合から外した修正（design.md 9.7.1）の実測確認** |
| flags-changed 経由の修飾キー計数 | LShift / LCtrl / LCmd に数字が付いた。**Command は「2〜3回タップ」という手順に対し実測 3 で、押下エッジ検出が正確** |
| `LSFT(KC_ENTER)` と素の Return の区別 | Shift+Return と Return が別の識別子として集計された |
| `英数` / `かな` | どちらも計数された。入力ソース一致だけを外した記録ゲートが機能 |
| パスワード欄 | 入力中 `secure-event-input enabled=true` が記録され、その間の打鍵は集計に現れなかった |
| ログの内容 | outcome のみ（`flush=ok days=1`）。キーコード・内訳はログに出ていない |
| レポート生成 | 実データと `--vil` から自己完結HTMLが生成され、3配列とも表示を確認 |

### 観測点の性質として確認できたこと

LShift の計数の大半は、`LSFT(KC_ENTER)` キーを打つたびにファームウェアが押す Shift に
由来していました（Shift+Return の計数とほぼ符合）。macOS から見れば実際に Shift が
押されているので正しい計数ですが、**「指が Shift キーを叩いた回数」とは一致しません。**
ヒートマップの修飾キー注記（押しっぱなしにするものは指別集計に入れない）の実例です。

### 未確認のまま残っていること

- **終了時 flush（`applicationWillTerminate` 経路）。** 次に `make stop` する機会に、停止直前の
  打鍵がファイルへ入ることを確認する。
- **日をまたぐセッションでのバケット切り替え。** このまま常駐を続ければ翌日確認できる。
- 2台目のMacへの配備は未実施。

## 2026-08-28 — SIGTERM で終了処理が走っていなかった（修正済み）

打鍵頻度の配備後に `make stop` を実測し、**`applicationWillTerminate` が呼ばれていない**
ことを確認しました。AppKit は SIGTERM にハンドラを入れず、既定動作はプロセスの即時終了です。

### 実測（修正前）

| 期待 | 実測 |
| --- | --- |
| 終了時の `key-frequency flush=ok` | 出ない |
| `summary transformed=… bypassed=…` | 出ない |
| 集計ファイルの更新 | mtime は直前の定期 flush のまま、合計も変わらず |

直前の定期 flush から停止までに打った分は失われていました。打鍵頻度は最大120秒ぶんを
メモリに持つため、この経路が塞がっていると `make stop` のたびにその範囲が消えます。

### 修正と実測（修正後）

`signal(SIGTERM, SIG_IGN)` で既定動作を外し、`DispatchSource` で受けて
`NSApplication.terminate` を呼ぶようにしました。同じ手順で再実測し、次の順で記録されました。

```
termination-signal received=SIGTERM action=terminate
summary transformed=0 bypassed=0 resets=0 synthetic-actions=0
```

`applicationWillTerminate` が走っています（この試行は打鍵ゼロのため flush は早期リターン）。

**影響は集計だけではありません。** event tap の解放と保留かなの破棄も同じ経路にあり、
これまで `make stop` では飛ばされていました。

### 保留打鍵ありでの終了時 flush と日またぎ（2026-08-29 追加実測）

通常の使用中に停止したところ、SIGTERM 修正の効果を保留打鍵がある状態で確認できました。

```
termination-signal received=SIGTERM action=terminate
key-frequency flush=ok days=2
summary transformed=47 bypassed=57 resets=0 synthetic-actions=48
```

**`summary` が 47 打鍵の変換を報告している状態で `flush=ok` が出ています。** 修正前は
この打鍵ぶんが失われていました。同じ行の `days=2` で、**日をまたいだバケットの切り替え**も
確認できています（記録時に暦日を決める実装のとおり、8/28 と 8/29 が別バケットになりました）。

### ログイン時起動での有効化

login agent は `--key-frequency` を渡さないため、ユーザーデフォルト
（`defaults write io.github.yuhkis.wkr-macos KeyFrequencyLog on`）がそのまま効きます。
`launchctl kickstart` で起動し直し、ログイン時と同じ経路（フラグなし）で
`conversion-started … key-frequency=on` を確認しました。plist は変更していません。
